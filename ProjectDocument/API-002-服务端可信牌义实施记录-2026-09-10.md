## 1. 任务目标

API-002 的目标是关闭 `/api/reading` 的牌义信任缺口：浏览器只负责提交用户实际做出的选择，牌名、关键词和基础含义全部由服务端依据 `cardId` 从仓库内的 `tarotCardMap` 读取。

本任务完成后，即使调用者绕过前端、直接修改 HTTP 请求并附加伪造的 `nameCn`、`nameEn`、`uprightKeywords`、`reversedKeywords` 或 `meaning`，这些字段也不会进入 DeepSeek Prompt。

## 2. 实施前状态与风险

API-001 已经建立运行时领域校验，可以拒绝错误牌数、非法或未知卡牌 ID、非法方向、重复牌位和重复卡牌。但当时为了分步迁移，浏览器仍会把以下字段发送给服务端：

- 中文牌名和英文牌名；
- 正位关键词和逆位关键词；
- 卡牌基础含义。

服务端虽然验证了这些字段的基本类型，却会继续使用客户端提供的内容构造模型输入。因此，直接调用 API 的攻击者可以保留合法 `cardId`，同时把牌义替换成任意文本，导致模型基于伪造数据生成结果。其影响包括：

- 解读结果不再对应用户真实抽到的牌；
- 客户端内容可能干扰 Prompt 的业务约束；
- 前端和服务端同时维护牌义，形成重复数据契约；
- 未来新前端必须了解不属于浏览器职责的内部字段。

## 3. 最终信任边界

### 3.1 浏览器可提交的事实

公开请求契约收敛为：

```ts
interface ReadingRequest {
  question: string;
  cards: Array<{
    cardId: string;
    position: "past" | "present" | "future";
    orientation: "upright" | "reversed";
  }>;
}
```

其中：

- `question` 是用户输入，仍属于不可信输入；
- `cardId`、`position` 和 `orientation` 是浏览器提交的抽牌事实，必须经过服务端校验；
- 任何额外字段均不会被复制到服务端可信对象。

### 3.2 服务端生成的可信数据

共享校验器在确认 `cardId` 存在于 `tarotCardMap` 后，重新构造内部对象并补充：

- `nameCn`；
- `nameEn`；
- `uprightKeywords`；
- `reversedKeywords`；
- `meaning`。

DeepSeek 适配层只接收 `TrustedReadingRequest`，并按已校验的 `orientation` 选择正位或逆位关键词。浏览器请求对象不会直接传给模型调用层。

因此当前数据流为：

```txt
浏览器抽牌事实
  -> Route Handler 解析未知 JSON
  -> validateReadingRequest 进行身份、牌位、方向和唯一性校验
  -> 按 cardId 查询 tarotCardMap 并重建 TrustedReadingRequest
  -> DeepSeek 适配层按 orientation 选择可信关键词
  -> 构造模型 Prompt
```

## 4. 实现内容

### 4.1 区分公开请求和服务端内部类型

`src/types/reading.ts` 将类型拆分为两组：

- `ReadingCardSelection` / `ReadingRequest`：浏览器与公开 API 使用的最小事实契约；
- `TrustedReadingCard` / `TrustedReadingRequest`：完成服务端校验和本地牌义补全后的内部契约。

这一拆分让 TypeScript 在编译期阻止 DeepSeek 适配层被误用为公开请求处理器，同时把运行时信任转换集中在共享校验器中。

### 4.2 浏览器停止发送牌义

`src/components/TarotExperience.tsx` 的请求构造只保留：

- `cardId`；
- `position`；
- `orientation`。

浏览器不再为了调用 API 查询并复制本地牌名、关键词或含义。旧前端仅做与后端联调相关的最小修改，未进入计划中被冻结的前端重做工作。

### 4.3 校验器负责可信规范化

`src/lib/reading-validation.ts` 在保留 API-001 全部领域规则和错误码的基础上：

- 删除对客户端牌名、关键词和含义的读取及类型校验；
- 使用已经验证的 `cardId` 查询 `tarotCardMap`；
- 创建新的 `TrustedReadingCard`，只复制本地数据源中的牌义；
- 对请求中的未知或伪造额外字段采取“忽略并丢弃”策略；
- 继续对问题执行现有非空校验和首尾空白清理。

选择忽略额外字段而不是因为额外字段拒绝整个请求，可以兼容尚未刷新、仍发送旧契约的客户端，但这些字段不再拥有任何业务影响。新前端应只实现最小公开契约。

### 4.4 模型调用只接收可信类型

`src/lib/deepseek.ts` 的 `requestDeepSeekReading` 参数改为 `TrustedReadingRequest`。构造 Prompt 时：

- 正位只使用 `uprightKeywords`；
- 逆位只使用 `reversedKeywords`；
- 牌名和含义均来自服务端补全后的对象；
- 不把另一方向的关键词传给模型。

这次没有修改现有 DeepSeek 模型、超时、错误分类和响应格式契约。

## 6. 验收结果

### 6.1 静态和构建检查

以下命令均通过：

```powershell
npm run lint
npm run typecheck
npm run build
```

生产构建成功生成首页、404、`/api/reading` 和应用图标路由。npm 仍会显示既有的 `strict-allow-scripts` 配置提示，本任务未扩大范围处理该提示。

### 6.2 本地 HTTP 与 Prompt 边界验证

使用本地受控 DeepSeek Mock 接收实际 `/chat/completions` 请求，未调用真实 DeepSeek，也未消耗线上余额。Mock 对最终 Prompt 执行白名单和黑名单断言：

- 必须出现仓库内可信牌名、实际方向、对应方向关键词和基础含义；
- 不得出现伪造的 `FORGED_NAME`、`FORGED_KEYWORD`、`FORGED_MEANING`；
- 不得把 `uprightKeywords` 或 `reversedKeywords` 这两个原始双向字段名传给模型。

HTTP 验收结果：

| 场景 | 状态码 | 结果 |
| --- | ---: | --- |
| 仅发送最小抽牌事实 | 200 | 通过 |
| 在合法请求中附加伪造牌名、关键词和含义 | 200 | 伪造字段被丢弃，Prompt 断言通过 |
| 使用未知 `cardId` | 400 | 返回 `UNKNOWN_CARD` |

测试中特别覆盖了愚者正位和魔术师逆位，确认服务端分别选择可信正位关键词“开始”和可信逆位关键词“欺瞒”。三个场景全部通过。

### 6.3 验收结论

API-002 的验收条件“直接篡改请求不能改变某张牌的名称、关键词和含义”已经满足。当前公开请求体不含牌义，服务端通过白名单式对象重建建立可信边界。

## 7. 保持不变的兼容行为

- API 路径仍为 `POST /api/reading`；
- 成功响应仍为 `past`、`present`、`future`、`summary`；
- 失败响应仍使用 `{ error: { code, message, retryable } }`；
- API-001 的卡牌数量、身份、牌位、方向和唯一性错误码保持不变；
- DeepSeek 不可用时，旧前端继续保留当前牌局并支持手动重试；
- 不生成假解读作为线上故障回退。
