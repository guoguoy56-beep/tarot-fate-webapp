## 5. 安装脚本与来源控制

锁文件中有两个带安装脚本的包：

| 包 | 范围 | 脚本/条件 | 决定 |
| --- | --- | --- | --- |
| `unrs-resolver@1.12.2` | ESLint 解析链路，开发依赖 | `postinstall` 检查平台原生 binding；缺失时可能从配置的 npm registry 获取对应 binding | 已审查并精确批准该版本 |
| `fsevents@2.3.3` | 开发依赖、可选 | 仅 Darwin，使用 `node-gyp rebuild` | 当前 Windows/Ubuntu 不安装、不批准；未来增加 macOS 环境时单独审查 |

控制措施：

- `.npmrc` 设置 `strict-allow-scripts=true`，未纳入白名单的安装脚本会使安装失败。
- `package.json#allowScripts` 只包含 `unrs-resolver@1.12.2`，不使用允许任意未来版本的名称级规则。
- `npm install-scripts ls` 返回无未审查脚本。
- `npm install-scripts prune --dry-run` 返回无无效白名单项。
- 禁止使用允许全部安装脚本的绕过参数。

npm 官方建议通过 `allowScripts` 管理安装脚本审批，并默认将批准项精确固定到版本：[npm install-scripts 文档](https://docs.npmjs.com/cli/v11/commands/npm-install-scripts/)。

## 8. 持续审计与升级纪律

### 每次依赖变更

1. 确认 Node.js 24 与 npm `11.19.1`。
2. 只在明确变更依赖时运行 `npm install`，并审查 `package.json` 与 `package-lock.json` diff。
3. 确认新增下载来源均符合预期，新增包具有 integrity。
4. 运行 `npm install-scripts ls`；任何新脚本先读源码和仓库信息，再精确批准版本或拒绝。
5. 运行 `npm run audit:all`、`npm run audit:prod` 和 `npm run check`。
6. 条件允许时运行 `npm run audit:signatures`；失败必须区分无效签名、缺失签名与远程服务不可用。
7. 推送后确认 GitHub `Quality gate` 全部通过。

### 定期与事件触发

- 每月至少一次：运行 `npm outdated`、全量/生产审计、安装脚本检查和签名核验。
- 每次公开发布前：重复完整检查，并生成/复核第三方依赖与许可证清单。
- 收到 Next.js、React、npm、ESLint 或直接依赖安全公告时：立即复核，不等待月度日期。
- high/critical 生产风险：停止发布，优先修复或移除；不能修复时必须明确暴露条件并由用户重新决定是否接受。
- 禁止未经评估运行 `npm audit fix --force`；主版本升级必须单独决策、验证和保留回滚点。
