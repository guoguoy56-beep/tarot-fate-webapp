# API-005：本地 DeepSeek 成本与故障保护实施记录

> 完成日期：2026-09-11
>
> 状态：已完成
>
> 适用范围：当前仅在本地开发与运行的塔罗牌 WebApp

## 1. 任务目标

API-005 在不引入管理后台、数据库、Redis、云服务或公开部署能力的前提下，为 `POST /api/reading` 建立最小但真实有效的成本与故障保护：

1. 可以通过本地配置立即暂停新的 DeepSeek 请求；
2. 单次生成存在明确的输出 Token 上限和超时上限；
3. 成功请求可以根据 DeepSeek 返回的 `usage` 统计实际 Token；
4. 余额不足、上游限流、上游错误、超时和异常响应可以从本地服务日志中区分；
5. 浏览器不获得成本指标、Provider 状态或任何敏感信息；
6. 不增加自动重试，也不生成假解读。

## 2. 范围与决策

### 2.1 本次实现的保护

- 新增人工熔断环境变量 `DEEPSEEK_READING_ENABLED`。只有值规范化后严格等于 `false` 时关闭在线解读；变量未配置时保持既有启用行为，避免破坏现有本地环境。
- 熔断检查发生在读取 API Key 和发起 `fetch` 之前。关闭时返回 HTTP 503、`DEEPSEEK_DISABLED`、`retryable: false`，不会产生上游请求。
- 保留既有 30 秒服务端超时，并将单次最大输出显式固定为 `1200` Token。
- 读取 DeepSeek HTTP 成功响应中的 `usage`，记录输入、输出、总 Token，以及可用时的缓存命中/未命中 Token；即使解读 JSON 随后校验失败，已经产生的有效 Usage 也会计入失败指标。
- 每个已经通过领域校验、准备进入 AI 调用阶段的请求输出一条 `[tarot.reading]` 结构化本地日志。
- 保留稳定的浏览器错误契约：`{ error: { code, message, retryable } }`。

### 2.2 本次没有实现的内容

- 没有每日金额硬上限。当前应用没有持久化层，进程内“每日金额”会在重启后失真；DeepSeek 价格也可能变化，硬编码人民币或美元费率会制造不可靠的预算判断。
- 没有创建管理后台、数据库、Redis、Vercel 项目或任何云资源。
- 没有实现公网匿名限流。该工作仍随 API-004 延期到未来 `REL-001`，并取决于届时的部署平台和真实客户端地址信任边界。
- 没有自动调用真实 DeepSeek 做验收，避免消耗余额；使用本机模拟上游完成生产形态 HTTP 测试。
- 没有修改旧前端视觉、交互或组件结构。

在当前“纯本地项目”的范围内，人工熔断比伪持久化的每日预算更可信。操作人可以依据 Token 累计值和错误分布判断是否继续启用；如果未来需要多人使用、跨重启预算或公网部署，再设计持久化配额。

## 3. 运行配置

本地 `.env.local` 示例：

```env
DEEPSEEK_API_KEY=your_api_key
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-v4-flash
DEEPSEEK_READING_ENABLED=true
```

### 正常启用

将 `DEEPSEEK_READING_ENABLED` 设为 `true`，或不配置该变量，然后重启本地 Next.js 服务。

### 紧急停用

将配置改为：

```env
DEEPSEEK_READING_ENABLED=false
```

随后重启 `npm run dev` 或 `npm run start`。新的合法解读请求会在本地被拦截，返回：

```json
{
  "error": {
    "code": "DEEPSEEK_DISABLED",
    "message": "在线解读已由本地配置暂停。",
    "retryable": false
  }
}
```

环境变量在 Node.js 进程启动时加载，因此修改后必须重启服务。不要通过修改前端代码或删除 API Key 来代替日常熔断操作。

## 4. 可观测指标

日志前缀固定为：

```txt
[tarot.reading]
```

每条日志包含：

| 字段 | 含义 |
| --- | --- |
| `outcome` | `success`、`failure` 或 `blocked` |
| `durationMs` | 本次 AI 阶段耗时，毫秒取整 |
| `upstreamRequested` | 是否实际尝试访问 DeepSeek |
| `model` | 成功响应实际报告的模型；缺失时使用请求模型 |
| `usage` | 本次上游 HTTP 成功响应报告的 Token 数据；上游未返回有效数据时省略 |
| `errorCode` | 项目稳定错误码 |
| `status` | 返回浏览器的 HTTP 状态 |
| `retryable` | 客户端是否可以向用户提供人工重试 |
| `providerStatus` | DeepSeek 原始 HTTP 状态；只写服务端日志 |
| `totals` | 当前 Node.js 进程生命周期内的累计计数和 Token |

`totals` 包含：

- `validatedRequests`：已经通过请求体和领域校验、进入 AI 阶段的数量；
- `upstreamRequests`：实际尝试访问 DeepSeek 的数量；
- `successes`：成功解读数；
- `failures`：已经尝试上游但失败的数量；
- `blocked`：被人工熔断或缺少 API Key 在本地阻止的数量；
- `promptTokens`、`completionTokens`、`totalTokens`：当前进程内、上游实际报告的累计 Token。

这些计数只存在于本地 Node.js 进程内，重启会归零。它们用于当前单机调试、演示准备和余额故障判断，不能宣称为跨进程审计账本。

请求体解析失败、超过 4096 字节、问题或卡牌领域校验失败时，请求尚未进入 AI 阶段，因此不计入 `tarot.reading` 指标。

## 5. 隐私与安全边界

结构化日志明确不写入以下内容：

- 用户问题；
- 卡牌列表、牌义和 Prompt；
- API Key 或 Authorization Header；
- DeepSeek 返回的完整解读；
- 原始请求体或原始上游响应体。

浏览器仍只收到 `past`、`present`、`future`、`summary`，或既有稳定错误对象。`usage`、累计计数和 `providerStatus` 不会进入公开响应。

## 6. 故障分类

| 场景 | 浏览器状态/错误码 | 是否实际请求上游 | 是否建议人工重试 |
| --- | --- | --- | --- |
| 人工关闭 | 503 `DEEPSEEK_DISABLED` | 否 | 否 |
| 未配置 Key | 503 `DEEPSEEK_NOT_CONFIGURED` | 否 | 否 |
| Key 无效 | 502 `DEEPSEEK_AUTH_FAILED` | 是 | 否 |
| 余额不足 | 503 `DEEPSEEK_INSUFFICIENT_BALANCE` | 是 | 否 |
| DeepSeek 限流 | 503 `DEEPSEEK_RATE_LIMITED` | 是 | 是 |
| 请求参数被上游拒绝 | 502 `DEEPSEEK_UPSTREAM_ERROR` | 是 | 否 |
| DeepSeek 5xx/网络故障 | 502 `DEEPSEEK_UPSTREAM_ERROR` | 是 | 是 |
| 30 秒超时 | 504 `DEEPSEEK_TIMEOUT` | 是 | 是 |
| 成功 HTTP 但响应结构无效 | 502 `DEEPSEEK_INVALID_RESPONSE` | 是 | 是 |

旧前端只有显式点击“重新请求解读”才会再次调用接口，并用请求中标记阻止同页并发重复提交；服务端没有自动重试 DeepSeek。发生故障时保留当前问题和抽牌结果，不自动伪造结果。

### 7.2 本地生产形态 HTTP 验收

测试通过本机模拟 DeepSeek 服务完成，没有发送真实 DeepSeek 请求：

| 验收项 | 结果 |
| --- | --- |
| 人工熔断返回 503，且模拟上游收到 0 个请求 | 通过 |
| 缺少 Key 返回明确配置错误，且模拟上游收到 0 个请求 | 通过 |
| 合法成功响应只向浏览器返回四个解读字段 | 通过 |
| 成功响应的 100/50/150 Token 正确记录和累计 | 通过 |
| 402 映射为余额不足，日志保留 Provider 402 | 通过 |
| 429 映射为限流，日志保留 Provider 429 | 通过 |
| 500 映射为可重试上游错误 | 通过 |
| 无 `choices` 的 200 响应映射为无效响应，且保留其中有效 Usage | 通过 |
| 非法领域请求不计为 AI 请求 | 通过 |
| 日志不包含测试问题和测试 API Key | 通过 |
| 测试结束后 3100/3101/3102/4010 端口无残留监听 | 通过 |

首次完整矩阵最终累计值为：5 个合法 AI 阶段请求、5 个上游尝试、1 个成功、4 个失败、0 个本地阻止、150 个总 Token；随后又单独验证了“200 但解读无效”的响应会保留并累计其有效 Usage，避免低估已经发生的消耗。

## 10. 回滚方式

如本次变更导致本地联调异常，可回滚 API-005 对应 Git 提交。紧急情况下无需改代码，只需将 `DEEPSEEK_READING_ENABLED=false` 并重启本地服务即可停止新的上游调用。回滚不得删除用户的 `.env.local` 或其他系统文件。
