核心判断：

1. **Next.js 14 必须升级。** Next.js 官方支持策略已将 14.x 列为不受支持版本；16.x 是 Active LTS，15.x 仅为 Maintenance LTS。
2. **直接升级到 Next.js 16.3.4，而不是先停在 15。** 项目体量小、App Router API 使用面窄，代码扫描未发现 14→15 和 15→16 的主要阻断 API；停在 15 只会增加一次中间迁移。
3. **React 与 Next.js 同步升级到 19.2.8。** 不保留 React 18 兼容模式，避免后续新前端再次做 React 主版本迁移。
4. **ESLint 一次迁移到 v10 原生 Flat Config。** 当前配置虽然文件名是 `eslint.config.mjs`，但内部仍通过 `FlatCompat` 转换旧式配置；升级时应移除该兼容层。
5. **TypeScript 不追最新主版本。** 当前生态中 TypeScript 已有更高主版本，但 Next.js 的间接 lint 依赖仍以 TypeScript 5/6 兼容区间为主；`5.9.3` 已在本项目通过类型检查，风险最低。
6. **Tailwind 4 和 Motion 13 延后。** 它们会直接改变旧前端样式/动效实现，与当前 P0 安全升级目标无关，应在新前端专项阶段集中处理。

## 4. 版本选择依据

### 4.1 Next.js 16.3.4

选择原因：

- Next.js 官方支持策略显示 16.x 为 Active LTS，15.x 为 Maintenance LTS，14.x 已不受支持。
- 2026 年 8 月安全公告要求升级到至少 16.3.3 或 15.5.24，以修复两个 Critical 漏洞。
- npm 稳定标签在决策时指向 `16.3.4`，因此选择高于最低安全补丁的最新稳定版。
- Next.js 16 要求 Node.js 20.9 及以上；项目已固定 Node.js 24 LTS，满足要求。

不选择的方案：

- 不选择 14.2.35：虽然是 14.x 较新补丁，但 14.x 已退出官方支持。
- 不选择 15.5.25：它仍受维护，但会把下一次主版本迁移留在项目重做过程中。
- 不选择 16.4 canary：预发布版本不用于恢复生产基线。

### 4.2 React / React DOM 19.2.8

选择原因：

- Next.js 16 面向 React 19.2 能力，并允许 React 19 稳定版作为 peer dependency。
- React 与 React DOM 必须保持完全一致的版本，避免渲染器不匹配。
- 项目已经位于 React 18.3.1。React 官方将 18.3 作为迁移到 19 前的告警版本，现有 `npm run check` 已通过。
- npm 稳定标签在决策时指向 React / React DOM `19.2.8`。

### 4.3 ESLint 10.10.0 与 eslint-config-next 16.3.4

选择原因：

- Next.js 16 已删除 `next lint`，要求直接使用 ESLint CLI；本项目现有脚本已经是 `eslint .`，无需修改命令语义。
- `eslint-config-next@16.3.4` 要求 ESLint 9 及以上，并原生提供 Flat Config。
- ESLint 10 支持 Node.js 24；项目运行时满足要求。
- 当前 `npm run check` 已显式执行 `lint → typecheck → build`。Next.js 16 不再在构建中自动运行 lint，不会降低本项目检查强度。

实施时必须：

- 将 `eslint.config.mjs` 改为直接导入 `eslint-config-next/core-web-vitals` 和 `eslint-config-next/typescript`。
- 保留现有忽略目录和 `TarotExperience.tsx` 的临时 `no-img-element` 例外。
- 删除 `FlatCompat`、`dirname`、`fileURLToPath` 和直接依赖 `@eslint/eslintrc`。

### 4.4 TypeScript 5.9.3

选择原因：

- Next.js 16 最低要求 TypeScript 5.1，`5.9.3` 满足要求。
- 当前实际安装的 `5.9.3` 已通过本项目 `tsc --noEmit`。
- `eslint-config-next@16.3.4` 间接使用 `typescript-eslint` 8.x；目标锁文件预计解析到支持 ESLint 10、并覆盖 TypeScript 5.9 的版本。
- 暂不升级 TypeScript 6/7，避免把语言服务器、编译器行为和框架迁移叠加到同一次 P0 改动。

### 4.5 Tailwind CSS 3.4.19

当前阶段明确保留 Tailwind 3：

- Tailwind 4 是主版本迁移，需要更新 PostCSS 插件、CSS 入口和配置方式。
- 当前项目使用 `tailwind.config.ts`、`@tailwind base/components/utilities` 和 v3 PostCSS 配置，迁移会直接影响旧前端呈现。
- Tailwind 官方说明 v4 面向 Chrome 111、Safari 16.4、Firefox 128；浏览器支持范围应在新前端阶段统一决定。
- Next.js 当前文档仍提供 Tailwind CSS v3 指南，因此保留 v3 不阻塞 Next.js 16。

因此 BASE-003 只把解析结果固化到 `3.4.19`，不执行 Tailwind 4 升级工具。

### 4.6 Framer Motion 12.43.0

当前阶段明确保留 Framer Motion 12：

- `framer-motion@12.43.0` 的 peer dependency 支持 React 18 和 React 19。
- 项目大量使用拖拽、翻牌、AnimatePresence 和手势动画，但当前尚无完整 E2E 回归保护。
- Motion 13 会改变部分属性过滤行为，官方同时推荐从 `framer-motion` 迁移到 `motion/react`；这属于新前端技术选型，而不是安全基线修复。

因此 BASE-003 不改 import 路径，不迁移 `motion` 包，只固定已验证的 v12 最新解析版本。

## 5. 代码兼容性扫描结果

### 5.1 Next.js 14 → 15

官方列出的主要破坏性变化包括异步 `cookies()`、`headers()`、`draftMode()`、动态路由 `params/searchParams` 和缓存默认值变化。

当前代码扫描结果：

- 未使用 `cookies()`、`headers()` 或 `draftMode()`。
- 没有动态路由参数或页面 `searchParams`。
- 没有依赖默认缓存行为的服务端 `fetch` 页面。
- 唯一 Route Handler 为 `src/app/api/reading/route.ts`，使用 `POST` 与 `NextResponse`，不受 GET 默认缓存变化影响。

结论：未发现 14→15 的源码级阻断项。

### 5.2 Next.js 15 → 16

当前代码扫描结果：

- 没有 `middleware` 文件，不涉及 `middleware` → `proxy` 重命名。
- 没有 AMP、`serverRuntimeConfig`、`publicRuntimeConfig`、PPR 或 `experimental.dynamicIO`。
- `package.json` 已使用 `eslint .`，不依赖已删除的 `next lint`。
- `next.config.js` 没有自定义 webpack 配置。
- `next.config.js` 使用官方仍支持的 CommonJS 与 phase 函数形式。

需要重点验证：

- Next.js 16 默认使用 Turbopack 执行 `next dev` 和 `next build`。
- 当前开发/生产分别使用 `.next-dev` 和 `.next` 的动态 `distDir`，必须验证两个命令不会互相污染。
- Next.js 16 构建不再自动执行 ESLint，因此必须继续保留 `npm run check` 的显式 lint 步骤。

结论：预计源码改动较少，主要迁移成本在依赖、ESLint 配置和构建验证。

### 5.3 React 18 → 19

已扫描以下常见阻断项：

- 未使用 `ReactDOM.render`、`hydrate`、`findDOMNode` 或 `unmountComponentAtNode`。
- 未使用字符串 ref、`propTypes`、`defaultProps` 或旧 context API。
- 未使用无初始值的 TypeScript `useRef<T>()`。
- 未使用 `react-dom/test-utils`、`react-test-renderer` 或旧 `act` 导入。
- 未使用 `useFormState`。

仍需在实际类型升级后验证：

- JSX、事件和 ref 的 React 19 类型变化。
- Framer Motion 拖拽事件的类型推断。
- 客户端水合期间是否出现新告警。

结论：静态扫描未发现明确阻断项，但交互流程必须做浏览器冒烟。

- 审查输出后，只接受与当前代码实际相关的转换。
- 不把 codemod 当作无条件批量改写工具。

### 第 3 步：成组更新核心依赖

必须在同一变更中更新：

- `next`、`react`、`react-dom`。
- `eslint`、`eslint-config-next`。
- `@types/react`、`@types/react-dom`、`@types/node`。
- 固化 TypeScript、Tailwind、Framer Motion、PostCSS 和 Autoprefixer 的目标版本。

禁止使用：

- `npm audit fix --force`
- `npm install --force`
- `npm install --legacy-peer-deps`

### 第 4 步：迁移 ESLint 配置

- 改用 Next.js 16 原生 Flat Config 导入。
- 删除不再需要的 `@eslint/eslintrc`。
- 保留项目现有定制规则与忽略目录。
- 先运行 `npm run lint`，仅修复升级新增且有依据的错误。

### 第 5 步：修复必要的类型或构建差异

- 运行 `npm run typecheck`。
- 运行 Next.js 16 默认 Turbopack 构建。
- `next build --webpack` 只作为诊断对照，不默认成为长期脚本。
- 不借升级机会重构 `TarotExperience.tsx` 或清理无关旧代码。

### 第 6 步：重建 lockfile

- 使用 BASE-001 约束的 Node.js 24 / npm 11。
- 重新生成 `package-lock.json`，清除无效、missing 和 extraneous 记录。
- 在一次性干净目录验证 `npm ci`，不以已有 `node_modules` 成功作为验收。

### 第 7 步：完整验证

按以下顺序执行：

1. `npm ci`（干净目录）
2. `npm ls --depth=0`
3. `npm run lint`

## 8. 回滚方案

### 8.1 回滚触发条件

出现以下任一情况，应停止扩展修复并回滚 BASE-003：

- 无法在不绕过 peer dependency 的情况下完成安装。
- 默认 Turbopack 构建存在短期无法定位的阻断。
- React 19 导致旧前端核心交互发生系统性回归。
- ESLint/TypeScript 需要大面积业务源码改写才能通过。
- 生产依赖审计结果没有实质改善。

### 8.2 回滚方式

- 将 BASE-003 保持为独立、可 revert 的提交。
- 优先使用 `git revert <BASE-003-commit>` 恢复依赖、配置和 lockfile。
- 已知升级前工程检查通过的代码参考点为 `129c4de`。
- 不删除本文档；回滚后记录失败原因并重新选择方案。
