## 3. 触发与权限设计

工作流名称为 `CI`，包含一个对外显示为 `Quality gate` 的作业。

触发条件：

- 推送到 `main`。
- 向 `main` 创建或更新 Pull Request。

权限与并发：

- 仓库权限限制为 `contents: read`，满足拉取代码所需的最小权限。
- 使用工作流名与 Git 引用生成并发组；同一分支或 Pull Request 出现更新时取消旧运行，只保留最新提交的结果。
- 使用 `pull_request`，不使用可接触目标分支权限和机密的 `pull_request_target`。

## 4. 运行时与安装策略

CI 不复制另一份版本号，而是优先读取仓库已固化的版本来源：

- Node.js：由 `.nvmrc` 提供主版本 `24`。
- npm：安装并校验 `11.19.1`，与 `package.json#packageManager` 和锁文件生成版本一致。
- 依赖：始终执行 `npm ci --no-audit --no-fund`，严格以 `package-lock.json` 为准。

版本校验不是只打印日志：脚本会在 Node.js 主版本不是 24 或 npm 版本不是 `11.19.1` 时以非零状态退出，避免托管环境悄悄漂移。

## 5. 质量门禁顺序

当前作业按下列顺序串行执行，任一步失败都会阻止作业成功：

1. 拉取当前提交。
2. 根据 `.nvmrc` 安装 Node.js，并配置 npm 下载缓存。
3. 安装 npm `11.19.1`。
4. 校验 Node.js/npm 实际版本。
5. 通过锁文件执行干净安装。
6. 执行 `npm run audit:all`；该步骤由后续 BASE-005 加入，对 high/critical 漏洞失败。
7. 执行 `npm run lint`。
8. 执行 `npm run typecheck`；该脚本会先运行 `next typegen`。
9. 执行 `npm run build`。

这里没有直接调用 `npm run check`，是为了让 GitHub Actions 明确展示依赖审计、Lint、类型检查与构建各自的失败步骤，降低诊断成本。BASE-004 首次运行时尚无第 6 步；当前状态以 BASE-005 的依赖风险记录和实际工作流为准。

## 6. 缓存独立性

`actions/setup-node` 的 `cache: npm` 只缓存 npm 的包下载目录，不缓存 `node_modules`，更不会跳过 `npm ci`。因此：

- 缓存命中时只减少下载时间。
- 缓存缺失或被删除时仍执行完整安装。
- CI 成功的事实来源是锁文件与安装命令，而不是某次运行遗留的依赖目录。

本地验收时把 `NPM_CONFIG_CACHE` 指向项目内新建的空目录，再执行 npm `11.19.1` 的 `npm ci`；命令从空下载缓存成功安装 389 个包，耗时 47 秒。验收后该临时缓存目录已删除。首次 GitHub 托管运行也在新作业环境中完成了锁文件安装和后续检查。GitHub 公共 API 可确认每个步骤结论，但未授权接口不提供原始日志，因此本记录不声称某个具体 GitHub 缓存键的命中状态。

## 9. 运维与失败处理规则

后续提交若出现红色 CI，应先根据失败步骤处理，而不是通过删除检查绕过门禁：

- 安装失败：检查运行时、npm 版本、依赖声明和 `package-lock.json` 是否同步。
- Lint 失败：修复规则违规，不在无评估时全局关闭规则。
- 类型检查失败：修复类型或路由类型生成问题。
- 构建失败：检查 Next.js 编译、环境变量边界和服务端/客户端模块使用。
- 缓存异常：可清理缓存后重跑；`npm ci` 必须仍然可独立完成。

若以后新增需要密钥的部署或真实 AI 冒烟，应建立独立、受保护的工作流，不把生产密钥暴露给普通 Pull Request。
