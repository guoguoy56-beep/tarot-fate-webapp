## 1. 任务目标

API-001 只解决三牌解读请求的运行时可信结构问题：

- 定义并校验卡牌 ID。
- 定义并校验 `past / present / future` 三种牌位。
- 定义并校验 `upright / reversed` 两种方向。
- 强制请求恰好包含三张牌。
- 拒绝重复牌位、重复卡牌和仓库中不存在的 `cardId`。
- 将校验从 Route Handler 中移到可复用模块。
- 为不同失败类别返回稳定、可测试的 400 错误码。

本任务不处理客户端牌义可信化、问题长度、请求体大小、限流和成本保护。这些内容分别属于 API-002～API-005。

---

## 2. 实施前状态

原 `src/app/api/reading/route.ts` 内部有一个私有 `isReadingRequest()`：

- 能检查问题非空、三张牌、三个牌位和部分字段类型。
- 不能被领域单元测试或其他服务端边界复用。
- 请求没有 `cardId`，无法验证卡牌是否属于仓库内 78 张牌。
- 没有检测重复卡牌。
- 所有输入错误只返回 `INVALID_REQUEST`，客户端无法稳定区分牌数、ID、牌位、方向和重复问题。
- 校验成功后直接把原始对象传给 DeepSeek 适配器。

这意味着“字段看起来像卡牌”可以通过，但服务端无法证明 ID 合法或三张牌互不重复。

## 3. 方案选择

### 3.1 手写校验与 Schema 库比较

| 方案 | 优点 | 成本/风险 | 本次决策 |
| --- | --- | --- | --- |
| 手写判别联合 | 零依赖、控制错误码和顺序直接、能复用现有 `tarotCardMap` | 规则增多时需要人工维护 | 采用 |
| 轻量 Schema 库 | 组合 Schema、错误路径和未来复用更系统 | 为一个小接口新增依赖、锁文件和供应链面；领域重复约束仍需自定义 refine | 暂不采用 |

当前请求只有一个根对象、一个三元素数组和少量枚举/字符串字段。主要复杂度不是结构嵌套，而是“已知 ID、牌位唯一、卡牌唯一”三项领域规则。现有 `Set` 和 `tarotCardMap` 已能清晰表达，因此新增 Schema 依赖没有足够收益。

若后续出现多条共享 API、大量可选字段或嵌套版本迁移，再重新评估 Schema 库；API-001 不为假设中的未来扩展预建框架。

### 3.2 共享校验结果

新增 `src/lib/reading-validation.ts`，导出：

- `isSpreadPosition(value)`
- `isCardOrientation(value)`
- `isTarotCardId(value)`
- `validateReadingRequest(value)`

`validateReadingRequest` 返回判别联合：

```ts
{ success: true, data: ReadingRequest }
```

或：

```ts
{ success: false, error: { code, message } }
```

路由不再理解每一项领域规则，只负责 JSON 解析、调用校验器、映射 HTTP 400 和调用 DeepSeek 适配器。

## 4. 请求契约变化

`ReadingCardPayload` 新增必填字段：

```ts
cardId: string;
```

旧前端构建请求时，从已经选中的 `PlacedCard.cardId` 传入该字段。一次合法的过渡期请求仍包含：

```ts
{
  question: string;
  cards: Array<{
    cardId: string;
    position: "past" | "present" | "future";
    orientation: "upright" | "reversed";
    nameCn: string;
    nameEn: string;
    uprightKeywords: string[];
    reversedKeywords: string[];
    meaning: string;
  }>;
}
```

这是一份过渡契约：API-001 用 `cardId` 完成身份、存在性和唯一性校验，同时暂时保留旧牌义字段以维持现有 DeepSeek 调用。API-002 才会删除浏览器提交的 `nameCn`、`nameEn`、关键词和 `meaning`，由服务端根据 `cardId` 重新生成可信数据。

因此，本次不能宣称“客户端牌义篡改风险已经消除”；它只是为下一步可信化建立了可靠 ID 基础。

---

## 5. 运行时规则

校验器按稳定顺序处理：

1. 根值必须是非数组对象。
2. `question` 必须是非空字符串；只执行现有的 trim，不增加最大长度。
3. `cards` 必须是数组且长度恰好为 3。
4. 每项必须是对象。
5. `cardId` 必须是非空字符串，并存在于 `tarotCardMap`。
6. `position` 必须属于 `past / present / future`，且三项不能重复。
7. `orientation` 必须属于 `upright / reversed`。
8. 三个 `cardId` 不能重复。
9. 过渡期旧牌义字段继续执行原有类型检查。
10. 校验成功后重建一个类型明确的新对象，不把未经选择的额外字段继续传入业务层。

当数组长度为 3、三个牌位均来自固定的三值集合且不重复时，三个牌位必然完整，因此不需要额外的“缺少未来牌位”分支。

## 6. 稳定错误码

所有下列错误均返回 HTTP 400，`retryable` 固定为 `false`：

| 错误码 | 触发条件 | 示例 |
| --- | --- | --- |
| `INVALID_REQUEST` | JSON、根对象、问题或过渡期牌义字段格式错误 | `{}`、`question: 42`、`nameCn: 42` |
| `INVALID_CARD_COUNT` | `cards` 不是恰好三项 | 两张或四张牌 |
| `INVALID_CARD_ID` | `cardId` 缺失、为空或不是字符串 | 缺少字段、`cardId: 42` |
| `UNKNOWN_CARD` | 字符串 ID 不存在于 `tarotCardMap` | `not-a-card` |
| `INVALID_CARD_POSITION` | 牌位不属于三个允许值 | `yesterday` |
| `DUPLICATE_CARD_POSITION` | 两张或更多卡牌使用同一牌位 | 两个 `past` |
| `INVALID_CARD_ORIENTATION` | 方向不属于两个允许值 | `sideways` |
| `DUPLICATE_CARD` | 三项中 `cardId` 重复 | `fool` 出现两次 |

错误响应外形保持不变：

```json
{
  "error": {
    "code": "UNKNOWN_CARD",
    "message": "解读请求包含未知卡牌。",
    "retryable": false
  }
}
```

没有切换成通用 `Result` 包装，也没有改变成功响应。
