## 1. 实施目标

BASE-003 的目标不是新增业务功能或重做前端，而是恢复工程基线的可信度：

1. 将存在已知风险且已脱离当前支持窗口的框架基线升级到受支持版本。
2. 重新建立由依赖声明生成、可被 `npm ci` 重放的锁文件。
3. 消除依赖树中的 invalid、missing、extraneous 和未审批安装脚本。
4. 迁移 Next.js 16、React 19 和新版 ESLint 配置要求。
5. 保持现有塔罗流程、视觉和 API 契约不变，并用构建、HTTP 与真实浏览器验证回归。

本任务明确未包含：新前端设计、业务功能扩展、API 安全加固、CI 配置和测试框架建设。它们继续按总计划独立实施。

## 3. 关键实施决策

### 3.1 npm 最低版本从 11.x 收紧到 11.19.1

在真实实施中，本机全局 npm `11.6.2` 即使重新安装，仍会生成不完整的 emnapi 依赖锁记录：`@emnapi/wasi-threads` 解析版本和它所需的 `@emnapi/core` 记录不一致，导致后续 `npm ci` 无法可靠重放。

使用 npm `11.19.1` 从依赖声明重新生成锁文件后，`@emnapi/core`、`@emnapi/wasi-threads` 及相关解析记录完整，`npm ci`、dry-run 与依赖树检查均通过。因此：

- `engines.npm` 收紧为 `>=11.19.1 <12`；
- `packageManager` 固定为 `npm@11.19.1`；
- 干净安装以 `npm ci` 为准，不能以旧 `node_modules` 能运行作为成功依据；
- 当前机器若尚未升级全局 npm，可使用 `npx --yes npm@11.19.1 <command>` 执行项目命令。

### 3.2 ESLint 10 方案改为 ESLint 9.39.5

BASE-002 预检时曾计划使用 ESLint `10.10.0`。真实解析显示：`eslint-config-next@16.3.4` 的顶层 peer 范围可以接受 ESLint 9 以上，但它带入的 `eslint-plugin-import`、`eslint-plugin-jsx-a11y`、`eslint-plugin-react` 当前 peer 范围尚未声明 ESLint 10。强行使用 ESLint 10 会留下 peer 警告或要求覆盖上游约束。

本任务以“依赖树无冲突、可稳定 CI”为优先级，最终选择 ESLint `9.39.5`，同时完成真正需要的原生 Flat Config 迁移。npm 已提示该 ESLint 9 版本不再处于上游支持期，因此这不是永久停留点；BASE-005 应记录并定期检查 Next.js 配套插件何时正式支持 ESLint 10。

### 3.3 原生 Flat Config

`eslint.config.mjs` 不再通过 `FlatCompat` 包装旧字符串配置，而是直接导入：

- `eslint-config-next/core-web-vitals`；
- `eslint-config-next/typescript`；
- `defineConfig` 与 `globalIgnores`。

因此删除了项目对 `@eslint/eslintrc` 的直接依赖。现有配置文件 CommonJS 规则例外、塔罗牌原图 `<img>` 例外继续保留，避免把工具链升级扩张成前端重构。

### 3.4 Next.js 16 输出目录与类型生成

旧配置通过开发阶段判断把输出切到 `.next-dev`。Next.js 16 已默认将开发构建隔离到 `.next/dev`，继续自定义目录会与新行为重叠。因此本次：

- 删除 `PHASE_DEVELOPMENT_SERVER` 和动态 `distDir`；
- 保留默认 `.next`，开发隔离由 Next.js 使用 `.next/dev` 管理；
- `tsconfig.json` 的旧 `.next-dev/types/**/*.ts` 改为 `.next/dev/types/**/*.ts`；
- 接受 Next.js 16 要求的 `jsx: react-jsx`；
- `typecheck` 改为 `next typegen && tsc --noEmit`，使路由类型可在检查前显式生成；
- 设置 `agentRules: false`，避免 `next dev` 自动在仓库根目录生成通用 `AGENTS.md`、`CLAUDE.md`，项目仍以已有规则文档为准。

### 3.5 安装脚本审批

npm 11.19.1 会检查依赖安装脚本。当前唯一需要执行安装脚本的直接相关包是锁定版本解析器 `unrs-resolver`，其脚本用于准备本机原生解析组件。项目在 `allowScripts` 中显式批准该包；真实安装后 `npm install-scripts ls --json` 返回空待审批列表。

## 4. 源码兼容修复

升级后的 React Hooks 规则识别出两处 Effect 内同步状态写入：

1. `TextReveal` 在 `text` 变化时同步清空文本；
2. 根体验组件挂载后同步把 localStorage 历史写入状态。

等价修复如下：

- `TextReveal` 由调用端按当前解读文本设置 `key`，文本变化时通过组件生命周期自然重置，不再在 Effect 开头同步写状态；
- localStorage 读取仍只发生在客户端，但状态更新放入 0ms 定时器回调，保持服务端首屏为空记录并避免 hydration 差异；卸载时清理对应定时器。

这些改动不改变用户流程、API 数据结构或视觉设计。

浏览器验证期间还发现 `/favicon.ico` 404。新增 `src/app/icon.svg` 后，Next.js 生成 `/icon.svg` 元数据路由，开发控制台恢复为 0 error / 0 warning。

## 5. 锁文件重建过程

1. 从 `package.json` 的精确版本声明出发，不复用旧 `node_modules` 作为锁文件正确性的依据。
2. 使用 npm `11.19.1` 在独立空目录生成新的 `package-lock.json`。
3. 核查关键包包含 `resolved`、`integrity` 和完整的 emnapi 依赖记录。
4. 将新锁文件放回项目根目录。
5. 执行真实 `npm ci --no-audit --no-fund`，共安装 389 个包并正常结束。
6. 检查顶层依赖树和安装脚本审批状态。

本次没有使用 `npm audit fix --force`，也没有用 `--legacy-peer-deps`、`--force` 或 overrides 绕过 peer 约束。
