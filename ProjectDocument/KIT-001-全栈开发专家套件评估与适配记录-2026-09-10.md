# KIT-001：全栈开发专家套件评估与项目适配记录

> 评估日期：2026-09-10
>
> 评估对象：`kit/AI用全栈开发套件包/`
>
> 项目基线：Next.js 16.3.4、React 19.2.8、TypeScript 5.9.3、Next.js Route Handler、DeepSeek API、localStorage
>
> 结论：部分适用；原套件保留为参考，不能原样启用；已将适用方法改造成仓库级 Codex 技能
>
> 后续任务：仍为 `API-001`，本次不改变产品功能和既定优先级

---

## 1. 评估目的

用户在项目工作区新增了“全栈开发专家”套件，希望在恢复项目建设前判断：

1. 套件能否被当前 Codex 工作环境识别和调用。
2. 套件采用的技术栈、架构规则和工作流是否适合本项目。
3. 原样使用会怎样影响当前实现、范围、进度和风险。
4. 若只有部分内容适合，应如何改造成项目专属、可控且可验证的工作方式。
5. 改造是否会提前启动前端重做、测试选型、数据库或其他尚未批准的工作。

本次只评估和建设工程工作流，不修改应用源码、不安装依赖、不执行套件内代码，也不提前实施 `API-001`。

### 2.2 对照的项目事实

评估以仓库中的实际状态为准：

- 服务端不是独立 Java 服务，而是 Next.js 16 App Router 的 Route Handler。
- UI 使用 React 19，不使用 Vue、Pinia 或 Element Plus。
- 当前只有 `POST /api/reading` 这一条主要业务 API，不是通用 CRUD 管理系统。
- 数据源是仓库内 78 张塔罗牌数据；用户历史存在浏览器 localStorage。
- 当前明确不做账号、服务端数据库、支付、后台、多牌阵和跨设备同步。
- 阶段 1 `BASE-001～BASE-005` 已完成，下一项唯一任务是 `API-001`。
- 前端整体重做已确认，但在 `FE-GATE` 前保持冻结，不提前决定组件、状态、视觉或动画路线。
- 测试工具要到 `TEST-001` 才正式选型，当前不能因套件示例直接锁定某个框架。

### 2.3 评估方法

本次完成了以下检查：

- 逐份阅读原套件 README、插件清单和八个 `SKILL.md`。
- 对照 `package.json`、API 路由、领域类型、塔罗数据、存储实现、总计划和 HANDOFF。
- 使用 Codex `skill-creator` 附带的 `quick_validate.py` 对八个原始技能逐一校验。
- 查询并打开 OpenAI 官方 Codex 技能文档，确认仓库级技能发现目录和最小格式。
- 按“适用内容、冲突内容、当前阶段、误触发风险、改造成本”逐项判断。

## 3. 总体结论

### 3.1 是否适用于本项目

结论是：**工程思想部分适用，技术实现大面积不适用，原包格式也不能直接作为当前 Codex 仓库技能使用。**

它适合提供以下通用工程提醒：

- API 输入、输出、错误、幂等与安全边界要明确。
- 代码审查应优先关注正确性、安全、稳定性和可维护性。
- 测试应覆盖正常、边界和异常路径，并隔离外部服务。
- 性能优化应先测量，再定位，再验证。
- 重构应小步、可回归并保持行为。

它不适合作为本项目的直接技术模板，主要原因是：

- 套件的默认后端是 Spring Boot + MyBatis-Plus，本项目是 Next.js Route Handler。
- 套件的默认前端是 Vue 3 + Pinia，本项目是 React 19，且新前端尚未完成专项决策。
- 套件以通用 CRUD、数据库和管理系统为主要模型，本项目是单主流程、无账号、无服务端数据库的沉浸式 WebApp。
- 套件中的统一 `Result` 包装、`/api/v1`、Java Controller/Service/Mapper 分层不是本项目的既有契约。
- 套件给出的固定行数、固定覆盖率和固定技术组合只能作为提示，不能代替本项目的风险与阶段判断。

### 3.2 决策

采用“保留原件 + 选择性重写 + 分阶段触发”方案：

- 原始 `kit/AI用全栈开发套件包/` 不删除、不移动、不覆盖，保留给未来其他 Java/Vue 项目参考。
- 不把原始八个技能直接加入本项目指令链。
- 把适用的工程方法重新编写为五个项目专属技能，放入 Codex 能识别的 `.agents/skills/`。
- Java、Vue、数据库三类能力在本项目中搁置。
- 前端组件开发技能不在此时改写；进入 `FE-GATE` 并完成前端专项决策后再创建，避免提前锁死新前端。

## 4. Codex 格式与发现机制评估

### 4.1 原套件是 Qoder 插件，不是 Codex 插件

`kit/AI用全栈开发套件包/.qoder-plugin/plugin.json` 明确声明了 Qoder 市场元数据和技能相对路径。该清单对原目标平台有意义，但不是 Codex 插件清单，也不会使当前 Codex 自动加载这些技能。

### 4.2 当前目录不会被 Codex 当作仓库技能目录

OpenAI 官方文档说明，Codex 会从当前目录到仓库根目录扫描 `.agents/skills`。任意 `kit/.../skills` 目录只是普通文件，不在仓库技能发现路径中。

因此，原套件放入工作区后的直接影响是：

- 不会改变应用构建、运行时、依赖或生产包。
- 不会自动约束 Codex 的实现行为。
- 只有在人工显式打开并照做时才会影响工作。

官方依据：[Build skills — Where Codex loads local skills](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills)。

### 4.3 八个原始技能均未通过 Codex 快速校验

在启用 UTF-8 模式后，八个技能得到同一类失败：

```text
Unexpected key(s) in SKILL.md frontmatter:
argument-hint, description_zh, user-invocable, version.
Allowed properties are:
allowed-tools, description, license, metadata, name
```

此外，原 `name` 使用中文。校验器要求 `name` 使用只包含小写字母、数字和连字符的 hyphen-case，因此即使删除上述字段，命名仍需改造。

这表示原文件可以阅读，但不能被视为已符合当前 Codex 技能规范。不能只把整个目录复制到 `.agents/skills` 后宣称适配完成。

## 5. 八项能力逐项适配判断

| 原技能 | 通用思想 | 可直接用于当前项目 | 决策 | 主要原因 |
| --- | --- | --- | --- | --- |
| API 接口设计 | 高 | 低 | 立即改造 | API-001～005 正好需要契约、安全和错误边界，但不能套用 CRUD、`/api/v1`、统一 `Result` 和 Java Controller |
| Vue 组件开发 | 低 | 无 | 搁置 | 技术栈冲突；当前是 React 19，且新前端方案尚未批准 |
| Java 业务开发 | 低 | 无 | 搁置 | 后端架构完全不同，引入 Spring/MyBatis 会造成项目重写和范围失控 |
| 代码审查 | 高 | 中 | 立即改造 | 审查维度通用，但应对齐 Next.js、React、DeepSeek、localStorage 和阶段冻结规则 |
| 单元测试 | 高 | 中 | 立即改造 | 测试分层有价值，但框架必须在 TEST-001 评估后选择，CI 不得调用真实 DeepSeek |
| 数据库设计 | 低 | 无 | 搁置 | 当前明确无服务端数据库；启用会与 MVP 和计划直接冲突 |
| 性能调优 | 中 | 低 | 改造后延后触发 | “先测量”适用，但 Java/JVM/SQL/Vue 内容不适用；实际重点是资源、78 张牌、动画和客户端包 |
| 重构建议 | 中 | 低 | 改造后仅显式触发 | 小步重构适用，但旧前端已冻结，不能借重构提前拆分或重写 `TarotExperience` |

### 5.1 API 接口设计

最值得保留的内容是状态码、请求校验、错误边界、幂等和安全意识。必须删除或改写的默认假设包括：

- 本项目不需要把 `/api/reading` 强行改为 `/api/v1/readings`。
- 现有错误契约是 `{ error: { code, message, retryable } }`，不能无理由替换成 `{ code, message, data, timestamp }`。
- 当前接口不是 CRUD，资源复数、分页、搜索和删除规范大多与当前任务无关。
- API-001 只做共享领域校验；服务端可信牌义、长度限制、限流和成本保护分别属于后续任务，不能一次性夹带。

### 5.2 Vue 与 Java 开发

这两项不是“稍微不匹配”，而是会改变项目架构：

- 用 Vue 模板指导 React 组件会引入错误的响应式、组件、状态和测试约定。
- 用 Java 分层指导 Next.js Route Handler 会制造不存在的 Controller/Service/Mapper/DO/VO 体系。
- 若按原模板搭建新服务，还会引入第二套运行时、构建、部署、鉴权、数据库和维护链路。

它们对本项目当前进度没有正向收益，反而可能把已完成的工程基线和既定总计划作废，因此明确搁置。

### 5.3 代码审查

保留 findings-first、严重度、证据和修复方向。项目化后重点增加：

- 三牌完整性、唯一性和服务端可信牌义。
- DeepSeek 错误、超时、余额不足和密钥边界。
- localStorage 损坏数据与迁移兼容。
- 旧前端冻结和 `FE-GATE` 的范围判断。
- 区分本次回归、已有问题和计划延后项。

### 5.4 测试

保留正常、边界、异常、Mock 和行为验证方法。项目化后不预设测试框架，并明确：

- `TEST-001` 才选择最小工具组合。
- CI 禁止访问真实付费 DeepSeek。
- 旧前端只保留一条核心 E2E 冒烟，不建立大规模视觉快照。
- 覆盖率是诊断信号，不采用脱离风险的统一 80% 硬指标。

### 5.5 数据库

当前历史记录由 localStorage 保存，项目计划多处明确“不引入数据库和账号”。数据库设计技能只有在未来用户明确扩展到登录、跨设备同步或后台时才重新评估；目前不启用，也不预留表结构。

### 5.6 性能与重构

二者保留方法论，但用阶段边界防止误用：

- 性能技能只在明确性能诊断或 `PERF-001/002` 时触发，基线关注资源加载、78 张牌、动画、视口、reduced-motion 和 API 等待。
- 重构技能只在用户或计划明确批准时触发；`FE-GATE` 前不得用它启动旧前端大拆分或新前端重写。

## 6. 已落地的项目专属技能

### 6.1 `tarot-api-engineering`

路径：`.agents/skills/tarot-api-engineering/SKILL.md`

适用：API-001～API-005 和 `/api/reading` 评审。它把当前契约、服务端可信数据、密钥边界、错误外形和五个 API 任务的分界写成固定检查项。

当前收益：下一步执行 API-001 时能减少“顺手完成 API-002～005”或套用通用 CRUD 模板的概率。

### 6.2 `tarot-code-review`

路径：`.agents/skills/tarot-code-review/SKILL.md`

适用：用户明确要求审查代码、diff、提交、API 或存储实现。它要求 findings-first、精确位置、触发条件和实际影响，并默认只报告不修改。

当前收益：审查会围绕本项目真实风险，而不是 Java/Vue 风格偏好。

### 6.3 `tarot-testing-strategy`

路径：`.agents/skills/tarot-testing-strategy/SKILL.md`

适用：TEST-001～006 或实际新增测试。它保留工具选型开放性，规定领域、适配器、API、存储和 E2E 分层，并禁止 CI 调用真实 DeepSeek。

当前收益：避免在 API 阶段因原套件示例过早加入 JUnit/Vitest/Jest 组合，也避免为即将替换的旧 UI 建设高维护成本测试。

### 6.4 `tarot-performance-audit`

路径：`.agents/skills/tarot-performance-audit/SKILL.md`

适用：用户明确要求性能诊断或进入 PERF-001/002。它聚焦浏览器和 Next.js 指标，不包含 JVM、MySQL 和 Vue 优化。

当前收益：技能已经可用，但通过触发边界不会影响当前 API 优先级。

### 6.5 `tarot-safe-refactoring`

路径：`.agents/skills/tarot-safe-refactoring/SKILL.md`

适用：用户或批准计划明确要求重构。它要求行为保护、小步验证和范围控制，并写明旧前端冻结规则。

当前收益：可以利用原套件的渐进重构思想，同时防止以“优化”为名提前启动新前端或扩展架构。

## 7. 对项目构建实现的影响

### 7.1 对生产应用

本次没有修改 `src/`、`public/`、`package.json`、锁文件、Next.js 配置或环境变量，因此：

- 不改变页面、API、DeepSeek 调用和 localStorage 行为。
- 不增加运行时依赖、客户端 JavaScript、构建时间或部署产物。
- 不改变 `/api/reading` 当前契约。
- 不解决也不掩盖当前 API 和存储已知问题。

`.agents/skills` 中只有 Markdown 指令，影响的是后续 Codex 执行方式，不进入 WebApp 生产包。

### 7.2 对工程工作方式

正向影响：

- API 阶段更容易守住每个任务的边界和验收。
- 测试、性能和重构不会因通用模板提前扩张。
- 审查会主动检查本项目最关键的可信数据、AI、存储和流程风险。
- 后续对话可通过技能描述自动匹配，减少反复重述完整背景。

需要注意：

- 技能不是项目计划的替代品；`HANDOFF.md` 和总计划仍是进度与范围权威来源。
- 技能不能证明代码正确；每项任务仍必须执行对应测试、类型检查、构建和人工验证。
- 技能内容以后若与用户最新决策冲突，用户当前要求优先，并应同步修订技能。

### 7.3 如果原样采用的负面影响

| 风险 | 可能结果 | 严重度 |
| --- | --- | --- |
| 用 Java/Spring 模板扩展后端 | 新增第二套服务、部署与依赖体系，已完成基线失去意义 | 高 |
| 用 Vue 技能重做前端 | React 技术路线被推翻，且绕过 FE-GATE 设计决策 | 高 |
| 强制统一 REST/Result 模板 | 当前 API 契约无需求地变化，前后端与后续测试返工 | 中高 |
| 现在引入数据库 | 违背 MVP 范围，增加账号、迁移、部署和隐私工作 | 高 |
| 现在锁定测试框架和覆盖率 | 抢跑 TEST-001，产生重复工具或为旧 UI 过度测试 | 中 |
| 现在按行数拆分组件 | 在保护测试不足时扰动核心流程，并与未来重做重复劳动 | 中高 |
| 无测量套用性能清单 | 花费时间优化非瓶颈，拖延 P0 API 安全工作 | 中 |

选择性改造已消除这些默认行为。

## 8. 对当前进度和计划的影响

### 8.1 进度结论

- 新增治理任务 `KIT-001`，状态为已完成。
- `BASE-001～BASE-005` 的完成状态不变。
- `API-001` 仍是唯一下一任务，尚未开始，也未因本次技能工作被标记为完成。
- API-002～005、DATA、TEST、AI、STORE、FE、QA/PERF、REL 等顺序不变。
- 前端整体重做仍冻结到 `FE-GATE`。

### 8.2 工期影响

本次只产生仓库指令和评估文档，不产生应用功能返工。它会带来很小的前置治理成本，但预计能减少以下后续浪费：

- API 各阶段相互夹带造成的返工。
- 误引入 Java/Vue/数据库技术栈。
- 测试框架未评估就落地。
- 旧前端在重做前被大规模重构。
- 把通用最佳实践误当成项目硬性架构。

不把这种收益换算成虚构的精确工期。后续仍以每个任务真实验收结果更新估算。

### 8.3 后续维护规则

- API 契约或阶段拆分变化时，更新 `tarot-api-engineering`。
- TEST-001 完成工具选型后，更新 `tarot-testing-strategy` 中的真实命令和目录。
- FE-GATE 批准后，单独决定是否创建 React 前端实现技能；在此之前不创建。
- 若未来批准账号或服务端数据库，重新评估数据库技能，不直接复用原 MySQL 模板。
- 技能修改后运行官方快速校验器；若 Codex 未发现变更，重启客户端检查。
- 不将用户提供的原始套件与项目适配版混写，保留来源和职责边界。
