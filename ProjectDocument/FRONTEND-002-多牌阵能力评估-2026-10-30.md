# FRONTEND-002：多牌阵与抽牌方式能力评估

日期：2026-10-30。性质：基于现有源码及离线测试的可行性评估，未实施多牌阵。

关联：[前端重建需求访谈](./FRONTEND-001-重建分支与需求访谈-2026-10-30.md)。网站暂定名为“命运回廊”；用户确认自动播放洗牌，再点击牌背使卡牌自动飞入牌位。本轮先完成所有牌阵的前端体验，新增牌阵真实解读与保存后续接入。

## 1. 评估结论

现有项目具备完整的 78 张牌数据、对应真实牌面、随机排列与随机正逆位，能够作为多牌阵共享基础。抽牌交互可统一为“自动洗牌 → 展开牌组 → 手动选择 → 按选定牌阵入位”，各牌阵分别规定张数、布局、牌位含义及解读目标。

当前实现只有“过去／现在／未来”三牌的完整流程。其余七类在明确业务规则后均有实现路径，但尚未具备可直接使用的抽牌、真实 AI 解读和历史保存闭环；不能只增加名称或改变布局便认为已经支持。新增牌阵的实际交付顺序及首版范围仍需与用户确定。

## 2. 现有能力与限制

| 环节 | 源码证据 | 对多牌阵的影响 |
| --- | --- | --- |
| 牌组与正逆位 | `src/data/tarotCards.ts:78`、`src/lib/tarot-random.ts:5`、`:16` | 可复用完整牌组与随机基础，不需要为每个牌阵另造一套牌组 |
| 牌位类型 | `src/types/tarot.ts:5` | 只允许 `past/present/future`，需要支持各牌阵自己的牌位标识 |
| 当前抽牌流程 | `src/components/TarotExperience.tsx:50`、`:311`、`:508`、`:536` | 固定三牌及三列布局，拖入第三张后自动请求解读；自动洗牌与新的手动选择体验需要在新前端实现 |
| 服务端请求 | `src/lib/reading-validation.ts:14`、`:69`、`:96` | 仅接受三张牌和上述三种牌位；单牌、更多张牌或新牌位会被拒绝 |
| 解读响应与 Prompt | `src/types/reading.ts:27`、`src/lib/reading-response.ts:8`、`src/lib/deepseek.ts:238` | 强制四个字段 `past/present/future/summary`，不能把关系或是非牌阵简单改个前端标题便获得对应解读 |
| 历史记录 | `src/lib/storage.ts:22`、`:32`、`:62` | 只认可当前三牌结构，最多保留 20 条；需增加版本与牌阵身份并兼容旧记录 |
| 请求与输出限额 | `src/lib/reading-limits.ts:2`、`src/lib/deepseek.ts:6`、`:7` | 当前请求体 4096 字节、输出上限 1200 Token、超时 30 秒；多牌后需重新核验篇幅、预算与耗时，不能直接认定沿用即可 |

旧验收材料中的“三组不同牌阵”指同一个过去／现在／未来牌阵的三组卡牌组合；`AI-001` 记录第 3 节明确表格顺序均为过去 → 现在 → 未来。这不代表已经实现三种牌阵。本次不改历史验收材料或论文。

## 3. 八类牌阵逐项评估

下表描述实现条件，不替用户指定最终的塔罗规则；张数和牌位不能仅根据名称推断。

| 用户提出的牌阵 | 当前完整支持 | 评估与待确定事项 |
| --- | --- | --- |
| 单排（若指单牌） | 否 | 具备从牌组选择一张的基础；需确认名称与一牌规则，增加单牌请求、解读和历史支持 |
| 是非牌 | 否 | 可用共享抽牌流程；先明确张数、如何处理正逆位及“是／否／不明确”等结果的判断依据，不能自行规定某种算法就是唯一标准 |
| 过去现在未来 | 是 | 领域流程、接口、解读与保存可复用；星空布局、自动洗牌及新的选择交互仍需重建 |
| 三牌阵 | 否，若牌位不同 | 三张牌的随机基础可复用；需明确与过去／现在／未来的差别，并为不同含义的牌位调整服务端与解读 |
| 十字牌阵 | 否 | 可设计对应空间布局；张数、交叉关系、抽牌顺序和牌位含义待确定，不能仅从“十字”认定具体版本 |
| 恋人十字牌阵 | 否 | 可复用抽牌基础；需定义关系视角、张数、牌位及组合解读规则，再接入对应布局与保存 |
| 暗恋牌阵 | 否 | 可实现；需明确主题、牌位与解读范围，并沿用不把未提供的他人心理或事件当作已知事实的既有解读边界 |
| 心之声 | 否 | 可实现；需先确定偏自我探索还是关系主题，以及张数、牌位和结果呈现 |

复杂牌阵的前端布局、AI 输出质量及等待体验尚未通过原型或真实请求验证。表中的可行性不代表这些功能已完成，也不代表已经确认工期。

## 4. 后续实现建议，尚未执行

1. 复用一套牌组与自动洗牌、手动选择流程；通过牌阵配置控制所需张数、牌位顺序和桌面布局。
2. 服务端保留可信牌义与请求校验边界：由可信牌阵定义核对数量、牌位和唯一性，不让客户端任意声称新的牌位含义。牌阵标识与新响应结构需在专项方案中明确。
3. 解读结构支持按牌位返回文本和整体总结，并保留与当前三牌响应的清楚版本边界；不要用过去／现在／未来的字段冒充其他语义。
4. 结合 `STORE-001～003` 处理存储版本、旧记录兼容和管理，避免新规则将原有历史当成坏数据丢弃。
5. 在确认每种规则后扩展相关校验、Mock、保存与新前端流程测试；常规验证继续隔离真实付费服务。
6. 最新交付范围已由用户明确为全量牌阵前端优先，新增牌阵的真实解读与保存后续接入。开发时可复用三牌建立共享主流程，但不能据此缩减首轮前端牌阵清单。

多牌阵的本地开发可以沿用现有 Next.js 本地服务；本轮不以购买服务器为前提。账号仍只做前端演示，论文保持原样。
