## 1. 任务目标

API-003 为 `POST /api/reading` 建立两层不可绕过的输入规模边界：

1. 用户问题最多 500 个 Unicode 字符，并明确空白和换行处理规则。
2. 整个请求体最多 4096 个 UTF-8 字节，超过限制时在 JSON 解析和领域处理前终止读取。

旧前端同步提供字符计数、超限提示和提交阻止，但本任务不开展视觉重做，也不实现频率限制、并发控制或成本熔断。

## 2. 最终规则

### 2.1 问题字符规则

| 规则 | 行为 |
| --- | --- |
| 最大长度 | 500 个 Unicode 码点 |
| 纯空白问题 | 返回 HTTP 400，错误码 `INVALID_REQUEST` |
| 首尾空白 | 在服务端进入 Prompt 前清理；旧前端开始仪式时同步清理 |
| Windows 换行 `\r\n` | 统一为 `\n` |
| 单独回车 `\r` | 统一为 `\n` |
| 内部换行 | 允许、保留并计入字符数 |
| 第 500 个字符 | 接受 |
| 第 501 个字符 | 返回 HTTP 400，错误码 `QUESTION_TOO_LONG` |

这里使用 Unicode 码点计数，而不是 JavaScript UTF-16 `string.length`。因此常见 emoji（例如 `😀`）按 1 个字符计数，不会因为代理对被计成 2 个。

500 字选择依据：项目原技术评估建议 300～500 字；选择区间上沿可以容纳有背景信息的关系、学业和职业问题，同时仍能限制 Prompt 输入规模。问题长度不是成本保护的完整替代，频率和预算控制仍分别属于 API-004、API-005。

### 2.2 请求体规则

| 规则 | 行为 |
| --- | --- |
| 最大大小 | 4096 个 UTF-8 字节 |
| 声明的 `Content-Length` 超限 | 不读取正文，直接返回 HTTP 413 |
| 未提供 `Content-Length` 的分块请求 | 逐块累计实际字节数，超过 4096 后停止读取并返回 HTTP 413 |
| 恰好 4096 字节 | 允许进入 UTF-8 解码、JSON 解析和领域校验 |
| 非法 UTF-8、空正文或非法 JSON | 返回 HTTP 400，错误码 `INVALID_REQUEST` |
| 超大请求错误码 | `REQUEST_TOO_LARGE`，`retryable: false` |

4 KiB 明显高于正常的三牌最小 JSON 请求，也足以容纳 500 个四字节 Unicode 字符及固定卡牌结构；同时远低于通用上传接口的大小，可以在进入 DeepSeek 调用前限制异常负载。

## 3. Next.js Route Handler 方案评估

当前接口是 App Router Route Handler，不是 Pages Router API Route，也不是 Server Action。Next.js 官方说明 Route Handler 使用标准 Web `Request` / `Response` API，并可通过 `Request` 方法读取正文：[Route Handler API Reference](https://nextjs.org/docs/app/api-reference/file-conventions/route)。

评估过的配置：

- `serverActions.bodySizeLimit` 只限制 Server Action，不适用于当前 `POST /api/reading` Route Handler：[serverActions 配置](https://nextjs.org/docs/app/api-reference/config/next-config-js/serverActions)。
- `experimental.proxyClientMaxBodySize` 只在使用 Proxy 时控制复制/缓冲上限；官方说明超限后请求仍会继续处理，而且该能力是实验性配置，因此不适合作为本接口返回稳定 413 的业务边界：[proxyClientMaxBodySize 配置](https://nextjs.org/docs/app/api-reference/config/next-config-js/proxyClientMaxBodySize)。

最终选择在 Route Handler 前置解析模块中直接读取标准 `Request.body` 流：先检查可信度有限但可快速失败的 `Content-Length`，再对实际流量逐块计数。即使调用者省略或伪造较小的 `Content-Length`，实际读取仍不能超过 4096 字节。

## 4. 实现内容

### 4.1 共享限制与规范化函数

新增 `src/lib/reading-limits.ts`，集中定义：

- `MAX_READING_QUESTION_CHARACTERS = 500`；
- `MAX_READING_REQUEST_BYTES = 4 * 1024`；
- `normalizeReadingQuestion`；
- `countReadingQuestionCharacters`。

浏览器和服务端复用同一问题上限与计数规则，避免前端显示 500、服务端却采用另一数值。

### 4.2 有界请求体读取

新增 `src/lib/reading-request-body.ts`：

- 读取前检查 `Content-Length`；
- 使用 `ReadableStream` reader 逐块读取；
- 以字节数而不是 JavaScript 字符数判断请求体大小；
- 超限时取消继续读取并返回 `too-large`；
- 只对限制内的完整字节数组执行严格 UTF-8 解码和 `JSON.parse`；
- 将非法正文与超大正文区分为稳定结果，不向外泄露解析异常。

`src/app/api/reading/route.ts` 保持薄路由职责：调用有界读取器、映射 400/413、调用共享领域校验，再进入 DeepSeek 服务。

### 4.3 服务端问题校验

`src/lib/reading-validation.ts` 在卡牌校验前执行：

1. 确认 `question` 为字符串；
2. 规范化换行并清理首尾空白；
3. 拒绝规范化后的空问题；
4. 使用共享 Unicode 计数器拒绝 501 个及以上字符；
5. 只把规范化后的问题写入 `TrustedReadingRequest`。

新增稳定错误码：

- `QUESTION_TOO_LONG`：HTTP 400；
- `REQUEST_TOO_LARGE`：HTTP 413。

两者均为调用者修改输入后才可解决的问题，因此 `retryable` 为 `false`。

### 4.4 旧前端必要反馈

`src/components/TarotExperience.tsx` 只做 API-003 所需的兼容修改：

- 显示实时 `当前字符数/500`；
- 允许正常内部换行；
- 501 字时显示明确提示并设置 `aria-invalid`；
- 空问题或超长问题时禁用“开始仪式”；
- 开始仪式时保存规范化后的问题；
- 字符计数与帮助文本通过 `aria-describedby` 关联输入框。

没有修改旧前端的页面结构、抽牌流程、视觉方向或组件架构。

### 4.5 文档契约同步

`ProjectDocument/DEMO开发文档.md` 的请求体已从旧的客户端牌义结构更新为 API-002 后的最小抽牌事实，并补充本任务的 500 字与 4096 字节规则。

| 场景 | HTTP | 错误码/结果 | 验收 |
