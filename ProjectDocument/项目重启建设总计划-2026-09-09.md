## 1. 文档目的

本文档是项目重启后的总执行计划。后续工作按本文档的阶段、优先级和验收条件逐步推进，不再以零散视觉优化或临时功能修改作为主要开发方式。

本文档解决四个问题：

1. 现在先做什么，后做什么。
2. 每个阶段解决哪些问题，不解决哪些问题。
3. 每项工作完成到什么程度才算通过。
4. 前端整体重做应该在什么时候开始，以及开始前必须具备哪些基础。

本计划不提前确定新前端的视觉细节、组件方案和具体实现路径。进入前端阶段时，将单独进行产品、设计、技术架构和迁移方案讨论，并形成前端专项方案后再编码。

## 2. 已确认的项目级决策

### D-001：前端整体重做

已确认：**当前前端将整体重新设计和实现。**

这里的“前端”暂按以下范围理解：

- `src/app/page.tsx` 的页面呈现与交互入口。
- `src/app/layout.tsx` 中与前端体验相关的页面元数据和壳层。
- `src/app/globals.css` 及后续样式体系。
- `src/components/` 下的页面组件、交互组件、动画和状态组织。
- 浏览器端历史记录展示、错误反馈和响应式体验。

以下内容原则上优先复用，而不是随前端一起推倒：

- `src/app/api/reading/route.ts` 的服务端路由能力，但需要先加固。
- `src/lib/deepseek.ts` 的上游调用和错误分类，但需要调整可信输入边界。
- `src/data/tarotCards.ts` 的 78 张牌数据，但需要校验和可能的内容完善。
- `src/types/` 中可继续使用的领域类型。
- `public/cards/rws/` 的 78 张 Rider-Waite-Smith 牌面。
- 当前背景、卡背和其他素材是否继续使用，留到前端专项讨论时决定。

最终边界将在“前端方案关口”再次确认。如果后续决定连产品流程或视觉定位也全部替换，应更新本计划，而不是在编码中静默扩大范围。

### D-002：先修基础，再做新前端

前端整体重做不作为项目重启后的第一项编码任务。优先顺序为：

1. 工程环境可复现。
2. 依赖和框架安全。
3. API 与数据边界稳定。
4. 核心逻辑可自动验证。
5. AI 服务恢复并可观测。
6. 再进入前端专项讨论和整体实现。

原因：如果先做新前端，后续框架升级、API 请求结构变化、存储格式变化和测试补建会反复冲击新代码，产生大量返工。

### D-003：旧前端进入维护冻结

从本计划生效后，当前 `TarotExperience.tsx` 及相关旧前端进入维护冻结：

- 不再按旧路线继续拆分 `TarotDeck`、`RitualTitle`、`CardRevealEffects` 等组件。
- 不继续投入旧前端的大规模响应式改造和视觉精修。
- 不在旧架构上增加新的牌阵、主题、历史管理大功能。
- 只允许修复会阻塞基础验证、临时演示、数据安全或后端联调的严重问题。
- 旧前端作为现有功能、动效、素材和用户流程的参考实现保留。
- 新前端达到功能等价和验收标准后，才删除旧前端代码。

### D-004：前端细节延后决策

以下问题现在不提前拍板：

- 新前端是否继续“旧女巫木桌风”。
- 首页、洗牌、抽牌和阅读的具体布局。
- 是否继续使用拖拽作为唯一抽牌方式。
- 是否采用状态机库、React reducer 或其他状态方案。
- 是否继续使用 Tailwind CSS 和 Framer Motion。
- 是否保留当前背景和卡背。
- 是原路由直接替换，还是通过独立 v2 路由/分支并行建设。
- 新前端的组件目录、设计系统和动效规范。

这些内容将在前端阶段开始前集中讨论，形成书面决定。

### D-005：不主动扩大产品范围

在新前端完成之前，暂不加入：

- 用户账号。
- 数据库和跨设备同步。
- 支付。
- 后台管理。
- 多种复杂牌阵。
- 社交分享社区。
- 与毕业设计主线无关的扩展功能。

若后续确实需要，应先说明目标、收益、成本和对工期的影响，再调整计划。

## 3. 总体目标与最终完成标准

### 3.1 总体目标

将当前“桌面端可展示 DEMO”建设为：

> 一个环境可复现、核心逻辑可测试、AI 接口安全可控、前端全新且支持桌面与移动端、能够稳定部署和用于毕业答辩的塔罗牌 WebApp。

### 3.2 最终完成标准

项目只有同时满足以下条件，才视为本轮重启建设完成：

#### 工程

- 在干净环境执行 `npm ci` 成功。
- Node.js/npm 版本有明确约束。
- Lint、类型检查、单元测试、API 测试、构建和核心 E2E 全部通过。
- CI 自动执行必要检查。
- 不依赖本机缓存、历史 `node_modules` 或未记录配置。

#### 安全与 AI

- 生产运行时依赖没有未接受的 critical/high 风险。
- API Key 只在服务端读取。
- 服务端只信任 `cardId`、牌位和正逆位，并从本地可信数据取牌义。
- 问题长度、请求规模、频率和并发受限制。
- AI 成功、认证失败、余额不足、限流、超时和异常格式均可验证。
- 公开环境有基本成本保护和非敏感日志。

#### 数据

- 78 张牌 ID、数据和图片路径完整且有测试。
- localStorage 有版本、运行时校验和损坏数据降级。
- 新旧前端之间的历史记录兼容策略明确。
- 用户能理解数据保存在本地，并可以删除。

#### 新前端

- 旧前端已经由新实现完整替换。
- 关键流程在桌面端和移动端都能完成。
- 提问、洗牌/选牌、三牌放置、AI 解读、命运手记、保存和历史功能闭环。
- 关键交互具备触摸和键盘替代方式。
- reduced-motion、焦点管理、弹窗语义和基本对比度达到项目标准。
- 视觉、动效和代码架构与批准的新前端专项方案一致。

#### 发布与交付

- Preview 和 Production 环境可部署。
- 部署后自动或手动冒烟通过。
- 有隐私说明、娱乐免责声明和素材许可记录。
- README、HANDOFF、技术报告和毕业设计描述与实际实现一致。
- 有稳定的答辩演示脚本和故障预案。

## 4. 优先级规则

### P0：阻塞后续建设

不完成就不进入新前端编码：

- 依赖锁文件和干净安装。
- 框架安全升级。
- Node/npm 版本固定。
- API 可信数据边界。
- 输入限制与基础成本保护方案。
- 核心领域逻辑测试。
- AI 真实服务恢复。

### P1：新前端开发与发布必须具备

- localStorage 版本和校验。
- 新前端专项方案。
- 新前端核心流程。
- 移动端和可访问性。
- E2E 测试。
- CI 与部署环境。
- 隐私和素材许可说明。

### P2：核心闭环后优化

- 更精细的动效和粒子。
- 资源格式和性能深度优化。
- 历史导出等增强功能。
- SEO、Open Graph 和分享体验。
- 更丰富的牌义内容。

### P3：本轮暂不安排

- 登录、数据库、支付、后台、多牌阵和社区能力。

## 8. 阶段 2：领域数据与 API 加固

### 8.1 目标

为新前端提供稳定、可信、可测试的业务契约，同时防止公开部署后的明显成本滥用。

### 8.2 目标请求契约

原则上将浏览器请求收敛为：

```ts
interface ReadingRequest {
  question: string;
  cards: Array<{
    cardId: string;
    position: "past" | "present" | "future";
    orientation: "upright" | "reversed";
  }>;
}
```

最终字段命名可在实现时微调，但必须保持：

- 客户端不能覆盖牌名、关键词和含义。
- 服务端用 `cardId` 查找仓库内可信数据。
- 三个位置唯一且完整。
- 卡牌不能重复。

### 8.3 任务清单

#### API-001：建立共享领域校验

- 定义牌 ID、牌位、正逆位和三牌请求的运行时校验。
- 决定使用手写校验还是轻量 Schema 库；先评估现有需求，不为单一路由引入过重依赖。
- 所有失败返回稳定错误码。

验收：

- 缺字段、错误类型、重复牌位、重复卡牌、未知 cardId 均返回 400。

#### API-002：服务端规范化牌义

- 前端只发送抽牌事实。
- 服务端查询 `tarotCardMap`。
- 服务端按正逆位选择关键词。
- Prompt 中不再包含客户端可伪造的牌义字段。

验收：

- 直接篡改请求不能改变某张牌的名称、关键词和含义。

#### API-003：限制问题和请求规模

- 前端显示字符计数和上限。
- 服务端独立执行长度校验。
- 明确空白、换行、超长问题的处理。
- 评估 Next.js Route Handler 的请求体限制方式。

验收：

- 超长问题在前端不可提交，绕过前端后服务端仍拒绝。

#### API-004：确定部署与限流边界

- 先确定目标部署环境，因为 Serverless 与常驻 Node 的限流实现不同。
- 定义匿名用户限额、时间窗口和并发上限。
- 防止单用户快速重复请求消耗余额。
- 不记录完整用户问题作为限流键或日志。

验收：

- 超出限额返回明确 429 错误。
- 限流在目标部署环境中真实有效，而不是仅对单进程有效。

#### API-005：成本与故障保护

- 定义每日预算或人工熔断开关。
- 将余额不足、限流和上游故障转为可观测指标。
- 保留当前“不自动生成假解读”的原则。

验收：

- 上游异常不会导致客户端无限自动重试。
- 管理者能判断失败原因和请求量。

#### DATA-001：塔罗牌数据完整性测试

- 验证总数 78。
- 验证 ID 唯一。
- 验证 22 张大阿卡纳和 56 张小阿卡纳。
- 验证牌面路径存在。
- 验证关键词、牌名和含义非空。

验收：

- 数据或资源缺失会在测试中失败，而不是运行时才发现。

#### DATA-002：随机逻辑规范化

- 用明确的 Fisher-Yates 实现代替随机排序。
- 验证不丢牌、不重复和不修改源数据。
- 保持正逆位规则清楚可测。

验收：

- 多轮测试始终输出完整唯一牌组。

### 8.4 本阶段不做

- 不设计新前端界面。
- 不决定洗牌动画表现。
- 不增加新的牌阵。
- 不把 localStorage 迁移到数据库。

### 8.5 预计工作量

约 3～5 人日；限流实现取决于部署平台选择。

## 16. 执行与变更流程

每一个任务遵循同一流程：

1. 从本计划选择当前最高优先级、依赖已满足的任务。
2. 开始前确认任务范围和验收条件。
3. 检查相关代码、文档和测试。
4. 建立可复现失败或现状基线。
5. 实现最小必要改动。
6. 先运行最相关测试，再运行 `npm run check`。
7. 检查 Git diff 和敏感信息。
8. 更新本计划状态、HANDOFF 和相关专项文档。
9. 提交 Git 并推送。
10. 进入下一项任务。

### 16.1 单任务原则

尽量不要在一个提交中同时做：

- 框架主版本升级和前端重设计。
- API 契约修改和大规模动画改造。
- 依赖更新和无关格式化。
- 新前端功能与旧前端清理。

这样可以让回归、评审和回滚保持可控。

### 16.2 分支建议

较大任务使用独立分支，例如：

- `codex/baseline-recovery`
- `codex/api-hardening`
- `codex/testing-foundation`
- `codex/frontend-v2`

最终是否通过 Pull Request 合并，可在阶段 1 建立 CI 时一起确定。

### 16.3 状态定义

| 状态 | 含义 |
| --- | --- |
| 未开始 | 尚未投入 |
| 进行中 | 当前正在处理，已有明确负责人和验收 |
| 待验证 | 实现完成，等待测试或用户确认 |
| 已完成 | 验收通过、文档更新、提交并推送 |
| 阻塞 | 缺少必须的外部条件或用户决策 |
| 取消/替代 | 不再执行，并记录替代任务 |

## 20. 风险与应对

### R-001：框架升级与前端重做互相干扰

应对：先完成阶段 1，再开始新前端。

### R-002：继续维护旧前端造成重复投入

应对：执行维护冻结，只修复基础和阻断问题。

### R-003：前端方案未定就开始编码

应对：Gate C 未通过不得开始正式实现。

### R-004：测试建设过度

应对：优先领域、API 和一条核心 E2E，不为旧 UI 建立庞大测试套件。

### R-005：AI 费用或服务不稳定

应对：Mock 与真实冒烟分离，增加限流、预算和透明故障预案。

### R-006：移动端再次被拖到最后

应对：新前端专项方案必须同时给出桌面和移动端布局；每个 FE 里程碑双端验收。

### R-007：毕业设计范围持续扩张

应对：新功能必须说明对答辩价值，并经过计划变更后才能进入。

### R-008：新前端无法达到旧版表现

应对：保留旧前端截图、流程冒烟和回滚提交；新实现通过 Gate D 后才删除旧代码。
