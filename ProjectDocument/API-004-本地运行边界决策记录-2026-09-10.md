# API-004：本地运行边界决策记录

> 日期：2026-09-10

## 1. 最终决定

用户明确确认：当前项目只是本地项目，尚未计划上传云端或公开部署。因此 API-004 现阶段不应选择 Vercel、Upstash 或任何其他云端基础设施，也不应让本地应用依赖外部 Redis 才能工作。

本轮纠偏结果：

- 撤销 `@upstash/redis` 生产依赖。
- 删除 Vercel 代理信任、HMAC 匿名标识、共享频率限制和并发租约代码。
- 删除 `RATE_LIMIT_TRUSTED_PROXY`、`READING_RATE_LIMIT_SECRET`、`UPSTASH_REDIS_REST_URL`、`UPSTASH_REDIS_REST_TOKEN` 配置要求。
- 删除仅由该实现引入的 `READING_RATE_LIMITED`、`READING_CONCURRENT_LIMIT`、`RATE_LIMIT_UNAVAILABLE` 错误码。
- `/api/reading` 恢复为 API-003 完成后的本地调用链：请求体限制、领域校验、服务端可信牌义、DeepSeek 调用和稳定上游错误映射。
- `npm run dev` 与 `npm run start` 均不需要 Redis 或云平台账号。

没有创建 Vercel 项目、Upstash 数据库或其他云端资源，也没有产生云服务费用。

## 2. 为什么撤销，而不是保留为“以后可能有用”

Vercel + Upstash 方案本身可以用于一种未来部署形态，但当前缺少两个关键前提：

1. 用户没有决定公开部署。
2. 用户没有选择实际部署平台和网络代理链。

限流的可信客户端地址、共享状态、时间窗口和失败策略都依赖真实部署环境。提前把某个平台写进运行时会造成以下问题：

- 本地 `next start` 在缺少 Redis 时返回 503，破坏本地生产形态验证。
- 增加一个当前没有业务价值的外部可用性依赖。
- 增加包、环境变量、运维和隐私说明负担。
- 把尚未作出的部署决定伪装成既定架构。

因此当前采取最小实现：把无前提的代码完整撤回，只在计划中保留未来触发条件。历史方案仍可通过 Git 提交 `d652842` 查阅，不在当前文档和运行时中继续占位。

## 3. 当前本地边界

当前应用通过以下方式运行：

```powershell
npm ci
npm run dev
```

或验证生产构建：

```powershell
npm run build
npm run start
```

在线解读唯一需要的外部配置是 DeepSeek：

```env
DEEPSEEK_API_KEY=your_api_key
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-v4-flash
```

这里的“本地项目”表示应用由用户自己的电脑运行、没有作为公网服务发布。开发服务器是否可被同一局域网设备访问取决于操作系统防火墙和启动参数；这不等同于已经部署到云端，也不应被当作公网生产安全边界。

## 4. API-004 的计划归属

API-004 当前状态使用计划中的“取消/替代”，不是“已完成”：原验收条件要求超限 429 且在目标部署环境真实有效，但当前没有公网目标环境，也不需要匿名公网入口保护。

剩余工作并入 `REL-001`。只有同时满足以下条件才重新启动：

- 用户明确提出公开部署或上传服务器。
- 明确目标平台是 Vercel、自有 Node.js 服务器还是其他环境。
- 明确是否有 CDN、反向代理、负载均衡和多实例。
- 明确可信客户端标识来源。
- 明确允许的外部依赖与费用边界。

届时重新决定：

- 是否需要匿名频率限制。
- 限额、时间窗口和并发上限。
- 单进程状态、共享 Redis、平台原生限流或其他实现。
- 429 错误码与 `Retry-After`。
- 限流服务故障时 fail open 还是 fail closed。
- IP/匿名标识的隐私披露和保留周期。

不直接恢复历史代码；必须按届时真实平台重新评估。
