## 5 项目定位与可以成立的研究主线

这是一个以塔罗主题为交互载体的 Web 工程实践。用户输入问题，参与洗牌与三牌选择，由第三方大语言模型生成对应解释，再保存到浏览器本地历史。当前重点是沉浸式交互、受约束的数据传递、模型服务集成及故障处理。

适合贯穿全文的问题：

- 如何把提问、洗牌、选择、阅读和保存组织成连续且可恢复的页面流程？
- 如何保证客户端选择与模型收到的卡牌身份、牌位和方向一致？
- 如何限制不可信输入、检查外部生成结果，并在服务异常时保留用户操作？
- 如何用分层测试区分领域规则、上游适配、路由契约和浏览器体验？

可以概括为工程设计与实现特点，不宜包装为全新机器学习算法或已证实的心理疗效。没有模型训练、微调、向量数据库或 RAG；服务端 Map 查表不等于已经建立专业知识检索系统。也没有用户实验足以证明沉浸感、满意度或情绪改善提升了某个百分比。

## 7 业务流程与前端实现事实

实际阶段类型：

```text
intro → question → camera-lift → shuffle → fan → draw → reading → final
```

对应入场、提问、镜头过渡、鼠标洗牌、展开、依次拖入三牌位、阅读、命运手记。

- 主体仍集中在 `src/components/TarotExperience.tsx`；`AmbientLightEffects.tsx` 负责环境光。不能把计划中的多组件重构写成现状。
- 同一批 78 张卡牌在首页和洗牌阶段连续渲染；洗牌通过指针轨迹改变卡牌视觉位置和角度，产生局部惯性与弹簧反馈。
- 洗牌结束后收拢并展开为底部弧形牌带；用户依次放置过去、现在、未来三张牌。
- 有效拖放按目标牌位边界判断，记录 `cardId`、牌位、方向和顺序；正逆位在放置时确定，之后保持。
- 三张牌完成后发起一次解读请求；成功后按牌位逐张翻牌和本地打字机展示，最后汇总到手记。
- 浏览器失败时保留问题及三张牌，展示错误并允许手动重新请求解读；不会自动生成假的成功结果。
- 请求中设置浏览器 AbortController 和在途请求保护；重置会取消当前请求，并重新生成牌组。
- 现有重置代码只清理部分显式保存的定时器；不要泛化成“全部异步任务均已完整清理”。

**必须写清：一次性完整 JSON 响应 + 前端打字机动画。当前没有 SSE、ReadableStream 或逐 Token 网络流。**

旧前端主要服务桌面演示。已有评估指出移动端拖拽和布局不完善；当前单条 E2E 的 1920×1080 Chromium 通过不能证明移动端或跨浏览器兼容。旧评估中的个别桌面问题可能已调整，应看当前代码/实测再判断，不无条件复述旧缺陷为现状。

## 8 卡牌数据和随机规则

`src/data/tarotCards.ts` 提供 78 张牌：22 张大阿尔卡纳、56 张小阿尔卡纳，四花色各 14 张。图像位于 `public/cards/rws/`，使用 78 张 JPG；卡背与桌面素材位于 `public/assets/`。

基础字段：`id`、`nameCn`、`nameEn`、`arcana`、`suit`、`number`、`uprightKeywords`、`reversedKeywords`、`meaning`、`image`。`tarotCardMap` 按 ID 建立查表。

小阿尔卡纳按点数/花色模板组合构造，关键词和基础描述相对简化。可写“完整 78 张卡牌的结构化基础数据”，不能据此声称“逐牌经过专家审核的专业塔罗知识库”。

`shuffleDeck` 先复制输入，再执行 Fisher–Yates：从末尾向前，在当前范围内选交换位置。时间复杂度 O(n)，副本空间 O(n)；支持注入确定性随机源，默认 Math.random，不修改生产源数组。

`randomOrientation` 的规则是 **random() > 0.5 为 upright，其余为 reversed**，恰好 0.5 是逆位。鼠标扰动是视觉反馈，随机牌序由随机函数产生；不能写成鼠标熵采集、加密随机或经过统计实验证明的绝对公平。服务端验证三牌合法性，也不等于能证明它们来自不可作弊的抽牌过程。

素材文件完整性测试验证数量、唯一 ID/路径、分类、必要文本、实际 JPG 和 JPEG 标记，不等于验证所有素材的版权许可或每张图像的美术语义。素材来源与许可整理仍须有独立证据，不能仅凭早期文档中的 Public Domain 目标就认定全部许可已经核验。

## 9 接口、可信边界与数据契约

### 9.1 请求与验证流程

唯一主要业务接口：`POST /api/reading`。浏览器提交 `question` 和三项 `cards`，每项仅含 `cardId`、`position`、`orientation`。

`src/app/api/reading/route.ts` 的流程：限制请求正文、严格 UTF-8 解码、解析 JSON、领域验证、服务端查表重建可信卡牌、调用 DeepSeek 适配器、记录不含正文的指标、返回统一成功或错误对象。

| 规则 | 当前实现 |
| --- | --- |
| 问题规范化 | CRLF/CR 统一为 LF，去首尾空白，保留内部换行 |
| 问题长度 | 规范化后 1～500 个 Unicode 码点，使用 Array.from 计数 |
| 请求体大小 | 整个 JSON 最多 4096 个 UTF-8 字节，非 4096 个字符 |
| 请求流 | 可用 Content-Length 提前拒绝；仍累计实际读取字节，超限取消读取 |
| 牌数 | 恰好三张 |
| 牌 ID | 必须存在于服务端 tarotCardMap，且三张不重复 |
| 牌位 | past / present / future，各一次 |
| 方向 | upright / reversed |
| 可信内容 | 名称、关键词和含义从服务端数据重建，客户端附加牌义不进入 Prompt |

用户问题仍是非可信文本。当前 Prompt 告知模型将 question 视为数据、不执行其中改变规则的指令；这是一项约束措施，不是已形式化证明防住所有提示词攻击。

### 9.2 成功响应及当前工作区新增约束

恰好四个字符串字段：`past`、`present`、`future`、`summary`。当前 `reading-response.ts` 与 `deepseek.ts` 的未提交实现已增加：

- 三段解读各 120～180 个 Unicode 码点；总结 60～100 个。
- 去除首尾空白再计数，标点、内部空格计入；这不是仅计汉字，也不是 JavaScript UTF-16 的 `.length`。
- 拒绝缺失、额外、空白、过短或过长字段。
- 上游 `finish_reason` 必须是 `stop`；截断或非正常完成即使看起来能解析也不作为成功。
- 不截断、不自动补字、不生成替代解读、不自动重试；失败返回 `DEEPSEEK_INVALID_RESPONSE`。
- 服务端和前端共用当前响应守卫；历史存储使用独立规则，旧短记录不会仅因新输出字数门槛而全部失效。

这些实现和相应测试在本次工作区测试中通过，但截至本次取证尚未有对应的新真实服务验收/远程 CI 证据。不能把 AI-001 旧样本的 3/3 成功套用到新字数契约上。

### 9.3 错误契约与 HTTP 状态

公开错误结构：`{ error: { code, message, retryable } }`。不把 provider 原始响应、Key、Prompt 或内部异常直接返回浏览器。

| 情况 | 公开错误及 HTTP |
| --- | --- |
| 无效 JSON/正文/领域输入 | 相应 INVALID_*、UNKNOWN_CARD、DUPLICATE_* 等，400 |
| 问题超长 | QUESTION_TOO_LONG，400 |
| 请求体超限 | REQUEST_TOO_LARGE，413 |
| 人工关闭 / 未配置 Key | DEEPSEEK_DISABLED / DEEPSEEK_NOT_CONFIGURED，503 |
| 上游认证 401 | DEEPSEEK_AUTH_FAILED，502，非自动可重试 |
| 上游余额 402 | DEEPSEEK_INSUFFICIENT_BALANCE，503 |
| 上游限流 429 | DEEPSEEK_RATE_LIMITED，**503** |
| 超时 | DEEPSEEK_TIMEOUT，504 |
| 上游故障/网络异常 | DEEPSEEK_UPSTREAM_ERROR，通常 502 |
| 格式、长度或完成原因无效 | DEEPSEEK_INVALID_RESPONSE，502 |
| 未知内部异常 | INTERNAL_ERROR，500 |

**上游 429 的错误映射不能写成本项目已经实施公网匿名限流，也不能误写成当前公开接口必定返回 429。**

## 10 DeepSeek 适配、保护和日志

当前代码默认 Base URL 为 `https://api.deepseek.com`，配置模型默认名 `deepseek-v4-flash`；请求路径为 `/chat/completions`。模型由环境变量指定，实际服务可能返回另一个模型标识，报告应区分配置名与上游返回名。

- API Key 仅在服务端读取，浏览器只调用同源接口。
- 当前采用非思考模式、`response_format: json_object`、`max_tokens: 1200`。
- 总等待边界为 30 秒，使用 AbortController + Promise.race，结束后清理超时定时器；不是平均实际响应需要 30 秒。
- `DEEPSEEK_READING_ENABLED=false` 可人工暂停新请求，关闭或缺 Key 时不调用上游；这是本地开关，不是按错误率自动熔断算法。
- 按配置、认证、余额、上游限流、超时、上游故障和格式问题分类。
- 当前工作区 Prompt 强化篇幅示例、牌名/方向、可行反思、非确定预言和专业风险提醒；程序的严格校验主要针对结构、字段长度及完成状态。自然语言语义质量仍需人工评估。
- 失败时保留牌局并手动重试，没有自动重试、离线假解读或自动模型切换。

日志前缀 `[tarot.reading]`，记录结果类别、耗时、模型、错误码、HTTP 状态、是否尝试上游、上游实际 Usage 和进程内累计数；不记录问题、牌阵、完整 Prompt、解读正文或密钥。累计计数随进程重启归零，没有多实例聚合、数据库监控、账户预算或自动费用硬限额。

历史记录保存在浏览器，不等于问题从未离开设备：真实在线生成时，问题和必要卡牌信息仍会经服务端发送到 DeepSeek。论文不应写成“数据完全不上传”或承诺第三方不会留存任何数据。

当前限制：

SQLite 可以与当前本地 Next.js 服务配合，具体驱动、运行模式和框架兼容性在实施时验证。优先评估与现有 Node 24 匹配的轻量方式；若引入依赖，须遵守锁文件与安装脚本白名单。不要仅为数据库章节改写整个技术栈。

### 20.2 三张候选表

| 表 | 候选字段 | 关系与约束 |
| --- | --- | --- |
| tarot_cards | id、name_cn、name_en、arcana、suit、number、upright_keywords、reversed_keywords、meaning、image_path | id 主键；对应真实 78 张牌；关键词可采用受校验 JSON 文本，具体设计实施时定 |
| readings | id、question、created_at、summary | id 主键；只保存用户主动选择保存的完整结果，不把失败请求写成成功记录 |
| reading_cards | reading_id、position、card_id、orientation、interpretation | reading_id 指向 readings；card_id 指向 tarot_cards；(reading_id, position) 联合主键；(reading_id, card_id) 唯一 |

关系：一条 reading 对应三条 reading_cards；一张 tarot_card 可出现在多次不同 reading 中。牌位与方向使用枚举 CHECK/领域校验。外键约束要在实际连接中启用并测试。每次恰好三张涉及跨行约束，应由仓储事务和领域逻辑共同保证，不能声称只写一个普通字段 CHECK 就能验证整组三行。

卡牌数据从现有生产牌组初始化，不手工复制一套含义后让两份数据悄悄分叉。删除一条记录时应连同三项详情一起处理；如何维持最近 20 条、是否提供单条删除/清空，要与原行为和后续 STORE 计划统一。

### 20.3 需要改动和决定的位置

1. 服务端数据库初始化、版本迁移和仓储模块；本地数据库文件进入 Git 忽略，只提交结构、初始化代码及必要合成种子。
2. 历史记录读写接口与页面调用；主占卜流程和已抽牌的失败恢复保持一致。
3. 原 localStorage 的兼容：先验证旧记录，设计可重入的导入/去重和失败回退；未成功导入前不删除用户旧数据。
4. 明确保存位置从“当前浏览器”变为“本机服务端文件”后的隐私、备份及数据保留说明；没有账号时不能宣称已完成多用户隔离。
5. 数据库错误、事务失败和重复保存的提示与测试；不能让保存失败影响仍可阅读的解读。
6. 公开部署继续延期。SQLite 文件的持久目录、容器/托管平台限制和多实例问题在发布时单独评估。
