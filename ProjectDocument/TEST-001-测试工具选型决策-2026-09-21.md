## 1. 结论

项目采用以下“完整但最小”的测试工具组合：

1. **Vitest**：统一承担 TypeScript 领域单元测试、DeepSeek 适配器测试和 Next.js Route Handler/API 集成测试；默认运行在 Node 环境。
2. **Playwright Test**：承担浏览器端 E2E；旧前端阶段只保留一条核心闭环，首期 CI 只安装和运行 Chromium。

不再把 Node.js 内置测试运行器作为长期主运行器；现有 7 项 `.mjs` 数据/随机测试在 TEST-002 迁移到 Vitest 后，统一由 `npm test` 执行。迁移完成前，现有 `npm run test:data` 与 CI 保持原样。

本次不选择也不安装 Jest、Cypress、jsdom、React Testing Library、MSW、Vitest Browser Mode、覆盖率插件或视觉快照服务。它们不是能力不足，而是当前阶段没有足以抵消维护成本的项目需求。

## 4. 候选方案比较

### 4.1 TypeScript、适配器与 API 测试

| 候选 | 优点 | 本项目代价 | 结论 |
| --- | --- | --- | --- |
| Node.js `node:test` | 零第三方依赖；现有 7 项测试已验证可用 | Node 直接执行 TypeScript 时忽略 `tsconfig.json`，无法直接解析项目的 `@/*` 路径；要覆盖 Next.js Route Handler、模块 Mock 和假时钟，需要继续增加自定义加载/解析胶水 | 不作为长期主运行器；现有测试迁移后退出 |
| Jest | Next.js 官方支持；生态成熟；模块 Mock 完整 | 需要 `next/jest`、路径映射和额外转换配置；官方常见 UI 方案还会引入 jsdom/Testing Library；与当前仅需 Node 环境的测试目标相比依赖和配置更重 | 兼容但不选 |
| Vitest | 原生面向 ESM/TypeScript；Mock、假时钟、快照和覆盖率能力按需可用；Next.js 有官方接入指南；一个运行器可覆盖 TEST-002～004 | 需要 Vite peer 依赖，并显式配置 `@/*` 别名 | **选用** |

项目实测依据：现有 Node 24 类型剥离只能顺利运行使用可擦除语法、且不经过 `@/*` 别名的模块。Node 24 官方文档也明确说明其轻量 TypeScript 执行不读取 `tsconfig.json`，`paths` 不会被转换。因此，继续扩展 `node:test` 会把成本转移到自定义运行胶水，而不是保持真正的“零配置”。

### 4.2 浏览器 E2E

| 候选 | 优点 | 本项目代价 | 结论 |
| --- | --- | --- | --- |
| Playwright Test | Chromium/Firefox/WebKit；网络路由拦截、拖拽、trace、截图和本地 `webServer` 能力集中；项目此前已用 Playwright 完成人工自动化验收 | 需要安装浏览器二进制；CI 运行时间高于单元测试 | **选用；首期仅 Chromium** |
| Cypress | Next.js 官方支持，交互式调试成熟 | 当前项目没有 Cypress 资产或独有需求；再引入一个同类浏览器运行器不会增加必要覆盖 | 不选 |
| Vitest Browser Mode | 可与 Vitest 共享生态 | 当前核心需求是完整业务闭环和真实页面导航，而不是浏览器内组件单测；仍需浏览器 provider | 当前不选 |

Playwright 不替代 Vitest：浏览器测试只验证少量跨层关键路径，业务边界和错误矩阵仍由速度更快、定位更清楚的 Node 环境测试承担。

## 6. 目标测试结构与命令

后续任务按以下最小结构落地：

```text
vitest.config.ts
playwright.config.ts                 # TEST-005 才新增
tests/
  unit/
    tarot-data.test.ts
    tarot-random.test.ts
    reading-validation.test.ts
    storage.test.ts
  integration/
    deepseek.test.ts
    reading-route.test.ts
  e2e/
    legacy-reading-flow.spec.ts      # 旧前端只保留这一条闭环
  fixtures/
    reading.ts                       # 成功/错误响应的共享 fixture
```

最终命令约定：

```text
npm test             -> vitest run
npm run test:watch   -> vitest
npm run test:e2e     -> playwright test
```

配置原则：

- Vitest 默认 `environment: "node"`。
- 在 `vitest.config.ts` 显式把 `@` 映射到 `src`；当前只有一个别名，不额外引入 `vite-tsconfig-paths`。
- 测试之间恢复 Mock、环境变量和计时器，防止状态泄漏。
- 不用 Vitest 渲染异步 Server Component；Next.js 官方明确建议这类组件走 E2E，后续新前端仍由 Playwright 覆盖该边界。
- 不默认启用 jsdom，不配置全局浏览器对象。
- 暂不设置覆盖率百分比门槛；先用 TEST-002～004 的明确用例矩阵固定关键规则，后续再按真实缺口评估 V8 coverage。
- 不建立旧前端组件快照库，不对动画帧或大段 DOM 做脆弱断言。

## 7. TEST-002～006 的职责分配

### TEST-002：领域单元测试

- 安装并配置 Vitest/Vite。
- 把现有 7 项 `.mjs` 测试等价迁移为 TypeScript，不减少断言。
- 补充请求校验、错误码映射和存储校验测试。
- 迁移完成后移除旧 `test:data` 的独立运行器入口，避免同一测试维护两份。
- 建立统一 `npm test`，并把 CI 的 `npm run test:data` 替换为 `npm test`。

### TEST-003：DeepSeek 适配器测试

- 用 Vitest Mock 全局 `fetch`，不得访问公网。
- 用假时钟覆盖 30 秒超时，不让测试真实等待。
- 隔离和恢复 `DEEPSEEK_*` 环境变量。
- 覆盖成功、非 JSON、缺字段、401、402、429、5xx、超时和网络异常。

### TEST-004：API 集成测试

- 直接调用 Route Handler 的 `POST(Request)`，验证实际 HTTP 状态和响应体。
- Mock DeepSeek 模块边界，不复制适配器实现。
- 覆盖合法请求、字符/字节上限、重复牌位/卡牌、未知卡牌和上游错误映射。
- 明确断言响应不包含 Key、Prompt、内部异常栈或其他敏感信息。

### TEST-005：旧前端最小冒烟

- 安装 Playwright Test 与 Chromium。
- 对本地生产形态应用执行一条流程：提问 → 开始 → 结束洗牌 → 抽三张牌 → 模拟 AI → 逐张揭示 → 手记 → 保存。
- 使用 `page.route("**/api/reading", ...)` 返回本地 fixture，不修改生产代码，不调用 DeepSeek。
- 只保留少量具有讨论价值的参考截图；失败时保留 trace/截图，成功时不长期堆积大体积产物。
- 首期不运行 Firefox/WebKit 矩阵；新前端稳定后再按跨浏览器风险决定是否扩展。

### TEST-006：Fixture 与 Mock 规范

- 收敛 TEST-003～005 已出现的成功、错误和三牌 fixture，避免各测试复制不一致 JSON。
- 常规本地测试和 CI 一律 Mock DeepSeek。
- 真实 DeepSeek 只允许人工或受控环境显式执行，并与 `npm test`、`npm run test:e2e` 分离。
- Fixture 不保存真实用户问题、API Key、完整 Prompt 或敏感日志。

## 8. CI 落地方案

TEST-001 不改 CI。后续按任务逐步变更：

1. TEST-002 将当前 `npm run test:data` 门禁替换为 `npm test`，仍在 Lint、类型检查和构建之前运行。
2. TEST-005 增加独立浏览器步骤或 job：安装 Chromium，启动本地生产形态服务，运行 `npm run test:e2e`。
3. 浏览器 E2E 不注入 `DEEPSEEK_API_KEY`，通过网络拦截返回 fixture。
4. 仅在失败时上传 trace/截图；不把本地 `.env.local`、缓存或测试产物提交到仓库。

常规 CI 的目标仍是：无需真实 API Key、无需云资源、无需外部付费服务即可完整通过。

## 9. 风险与控制

| 风险 | 控制措施 |
